# Changelog

All notable user-facing changes to ProofCoder are recorded in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Version numbers will follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) from the first tagged release.

No version has been tagged yet. Planned versions and stages are tracked in the [roadmap](docs/ROADMAP.md).

## [Unreleased]

### Added

- Licensed under the [Apache License 2.0](LICENSE).
- `proofcoder serve`: a local browser interface that runs the same bounded agent loop as `run`, with a workspace picker, live event rendering, run history replay, an environment self-check, and a stop button ([ADR-0002](docs/adr/0002-local-browser-interface.md)).
- Cooperative cancellation for the agent loop, used by the browser stop button. A cancelled run ends as `interrupted`.
- Project governance documents: development specification v3.0, the [roadmap](docs/ROADMAP.md), [architecture decision records](docs/adr/README.md), this changelog, `CLAUDE.md`, and a pull request template ([ADR-0001](docs/adr/0001-document-governance.md)).
- Run checkpoints: before its first model call, every run records a content-addressed copy of the workspace baseline under the ignored `.proofcoder/checkpoints/<run_id>` directory, and a `checkpoint` trace event reports what it covers and what it does not. The baseline is captured by scanning rather than by intercepting writes, so a later rollback covers changes made by an allowed workspace script, build, or test as well as those made by the built-in file tools. Sensitive paths such as `.env` contribute neither content nor a content digest and are never written back; oversized files, ignored directories, symbolic links, and anything outside the workspace stay uncovered and are reported. A capture failure ends the run as `checkpoint_error` before the provider is contacted, `proofcoder run --no-checkpoint` starts without one, and the three most recent checkpoints are kept under a total size limit, pruned before each capture and never removing a run trace ([ADR-0004](docs/adr/0004-workspace-checkpoints.md)).
- Rollback planning and application for a recorded checkpoint, with per-path sources, a preview of every action, and a result that names each restored, recreated, deleted, skipped, and failed path.
- `proofcoder rollback`: `list` shows stored checkpoints, `show` prints everything a rollback would change without writing, `apply` restores the workspace to one run's baseline after printing that plan and obtaining confirmation, and `delete` removes one checkpoint. `--yes` skips the prompt for unattended use; without it a non-terminal standard input refuses rather than assuming an answer. Exit code `3` means confirmation was declined and nothing changed, `1` that at least one path could not be restored. Each rollback records its own trace under a new run ID whose `rollback` event names the run it undid, so `proofcoder trace list` shows it with status `rollback`.
- Rollback verification in the evaluation pipeline: a fixture may declare `verify_rollback`, and the runner then rolls the attempt back after scoring it and compares the workspace file-by-file with the snapshot taken before the agent started. An incomplete rollback, a workspace that does not return to that baseline, and a run with no usable checkpoint are each their own failure reason, and every attempt record carries what the rollback restored and what it could not. The new `rollback-word-wrap` fixture is the one that declares it.
- The `cleanup-text-helpers` evaluation fixture: a rename-and-delete task that also declares `verify_rollback`. Its solution moves one module, deletes a superseded copy, and repoints the importer, so the rollback check has to recreate deleted files and remove a created one instead of only restoring edited text, and its tests are outside the files the task may change.
- Rollback in the browser interface: the card that closes a run opens the same plan, and a second explicit confirmation applies it. Because a browser cannot be asked at a terminal, the server issues a digest with the plan and refuses any confirmation whose digest no longer matches the plan that would run now, returning the replacement plan for review; a workspace with a run in progress is refused outright. The page also renders each run's checkpoint coverage and shows recorded rollbacks in its history by the run they undid.
- Documentation consistency checks in `scripts/compliance_check.py`: registered tools must match specification section 7 and the README tool table, ADR records must agree with the ADR index, roadmap status values must be valid, and every path in the specification's directory layout must exist.

### Changed

- The `nodejs-word-count` evaluation fixture: the first bundled fixture that is not a Python project. Its tests run under Node's own test runner, which the built-in command policy does not know, so the fixture ships a `proofcoder.toml` and its metadata names it. That naming is the authorization — fixture metadata is never copied into the attempt workspace, so the workspace still grants itself nothing. Both the agent's run and the independent validation use that policy. Evaluation always runs with approval mode `never`, so a fixture's validation command must be an `allow` entry.
- The `nodejs-word-count` fixture recognizes its own failing state through a custom assertion message rather than through a line that only one of Node's test reporters prints. Node picks a reporter by version and by whether output is a terminal, so the previous anchor made the fixture refuse to run on some installations.
- Evaluation fixture metadata moves to schema version 3: every `fixture.json` now declares `command_policy`. Existing fixtures set it to `null` and are unchanged in behavior.
- `proofcoder run` gains `--approval` and `--command-policy`. `--approval on-risk` prints the full argv, working directory and timeout of a command that needs confirmation and waits for an answer; anything but an explicit yes refuses, and standard input that is not a terminal refuses immediately rather than assuming. `--command-policy <path>` is the only way a project policy takes effect; a `proofcoder.toml` sitting in the workspace is reported as found-and-not-loaded and changes no decision. The browser interface asks on the page: the request appears while the run waits, and the decision carries back the digest of the request that was displayed, so an approval can never land on a different command. A stop pressed while a request is on screen refuses it.
- The command decision becomes three-valued: allow, needs confirmation, or deny. Git's local write subcommands (`add`, `commit`, `checkout`, `reset`, `stash` and the rest) move from refused-outright to needing confirmation, and an approval protocol decides what happens next: an approval runs the command, a denial or a timeout refuses it as an ordinary structured result the run can continue past, and an interruption is recorded as an interruption rather than as consent. The wait for a person is excluded from the run's time budget, because `max_seconds` bounds the agent's work and a person deliberating is not that work. Every request and decision is recorded as an `approval` trace event ([ADR-0006](docs/adr/0006-command-policy-and-approval.md)).
- Git's network subcommands and `git config` stay refused outright rather than becoming confirmable. Network subcommands move repository content past anything a rollback reaches, and `git config` can set `core.hooksPath` or an alias that turns a later ordinary Git command into arbitrary execution.
- A project may declare additional allowed commands in a `proofcoder.toml` policy file, parsed with the standard library and loaded only when a caller names it. Because the file is repository content, it never authorizes itself: it is frozen for the run once read, must state each command's subcommands, options, decision and evidence kind rather than allowing a bare program name, may not redeclare any executable the built-in policy already decides, fails to load as a whole rather than in part, and is refused by every write tool at any path named `proofcoder.toml`.

- Evaluation fixture metadata moves to schema version 2: every `fixture.json` now declares `verify_rollback`. Existing fixtures set it to `false` and are unchanged in behavior.
- The evaluation report gains a dated section 14 for evaluation `2ed0188dfbb449a69d78bee13c538dbf`, the real-model repeated runs of the `nodejs-word-count` fixture: 3 of 3 attempts succeeded, and because that fixture's validation command exists only under the project policy its metadata names, the run is the evidence the stage H exit criteria were waiting on. The section also records what three runs cannot establish, and that evaluation raises no approval request, so the confirm side of the decision still has offline coverage only.
- The evaluation report gains a dated section 12 for evaluation `812e545045eb4f9ab3fa51ae2e109d7e`, the real-model repeated runs of the two rollback fixtures: 6 of 6 attempts succeeded and no rollback left an unrestored path, which is the evidence the stage F and stage G exit criteria were waiting on. The section also records what six runs cannot establish.
- Cross-run sessions: several runs in one workspace can now belong to one session, and a later run starts with a bounded, program-generated account of the runs before it rather than with nothing. What crosses is a summary, never the earlier run's messages, and each carried run keeps the program's observations and that run's own account of itself in separate labelled blocks. The carry is prefixed to the task message rather than added to the system instruction, and is trimmed to a fraction of the context budget before the run starts -- oldest account first, then oldest run entirely -- so a long session cannot make a run fail before its first model call. Verification never crosses: session data reaches no run-state field, so a run counts as verified only from a command it ran itself, and the earlier run's verification is carried marked expired rather than hidden. A stored session validates all-or-nothing with every field, count and total size bounded, is redacted like the trace before it is written, and each run records what it carried as a `session` trace event. There is no command-line or browser entry point yet ([ADR-0007](docs/adr/0007-cross-run-sessions.md)).
- The development specification defines the Stage I cross-run session constraints in new sections 9.5, 10.6 and 13.6: a session carries a program-generated summary rather than the previous run's message history, and that summary must keep program-owned facts visibly separate from what the previous run said about itself; the carried text is a delimited prefix of the task message, never appended to the system prompt, and is trimmed to a hard ceiling before the run starts rather than during it; session data reaches the prompt and nothing else, so a run can only be verified by a command it ran itself, and the previous run's verification is carried but marked expired rather than hidden; and because an allowed workspace process can write the run-artifact directory, a session file is forgeable and its model-authored half is treated as untrusted content, carries nothing that changes a decision, and loads all-or-nothing ([ADR-0007](docs/adr/0007-cross-run-sessions.md)).
- The development specification defines the Stage H command-policy and approval constraints in rewritten section 10.4: the command decision becomes three-valued (allow, confirm, deny); a project may declare extra allowed commands in a workspace file, but that file is repository content and so is loaded only when the user names it on the command line, is frozen for the run once read, and can never relax the non-overridable deny set; an approval timeout counts as a refusal and lets the run continue, the wait is excluded from the run's time budget, and an interruption is recorded as an interruption rather than as an approval; and whether a command counts as verification evidence is decided by its kind, not by whether it went through approval ([ADR-0006](docs/adr/0006-command-policy-and-approval.md)).
- The README states that the secret scanner's `history` scope requires Git 2.44 or newer.
- The development specification's scope and non-goals were revised for the v3.0 roadmap ([ADR-0003](docs/adr/0003-v3-scope-revision.md)).
- Four file tools, taking the local tool set from seven to eleven: `patch_file` applies several exact replacements to one file in a single atomic write and leaves the file untouched if any edit does not match; `make_directory` creates a directory and any missing parents; `delete_path` removes one file, one empty directory, or one symbolic link and never recurses; and `move_path` renames or moves without ever overwriting its destination.
- `create_file` gains an `overwrite` parameter, default `false`, which replaces an existing regular file and returns the before-and-after diff. Directories and symbolic links are never replaced.
- `delete_path`, `move_path`, and `create_file` with `overwrite: true` refuse to run when the run has no checkpoint, returning `CHECKPOINT_REQUIRED`. Availability is decided by the run, not by any argument the model supplies, and the tools that only add or edit content are unaffected ([ADR-0005](docs/adr/0005-destructive-file-tools.md)).
- The development specification defines the Stage G file-tool constraints in new section 10.5.6: deletion is limited to one file or one empty directory and never recurses, overwriting stays refused by default and is opened one call at a time, multi-edit patches are exact replacements applied atomically, and the destructive tools refuse to run when the run has no checkpoint ([ADR-0005](docs/adr/0005-destructive-file-tools.md)).
- The development specification defines the Stage F workspace checkpoint and rollback constraints in new sections 10.5 and 13.4: a content-addressed baseline captured before the first model call, rollback that covers changes made by allowed workspace processes as well as the built-in file tools, sensitive paths recorded as metadata only and never restored, and a bounded retention policy ([ADR-0004](docs/adr/0004-workspace-checkpoints.md)).

## Baseline before this changelog

The `0.1.0` version in `pyproject.toml` covers development stages A–E: the DeepSeek client, the repository-owned agent loop, the seven local tools, the default-deny command policy, evidence-gated completion, sanitized JSONL traces, the `doctor`, `run`, `trace`, and `eval` commands, and offline cross-platform CI with compliance and secret scanning.
