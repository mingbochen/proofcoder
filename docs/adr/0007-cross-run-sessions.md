# ADR-0007：同一工作区内的跨运行会话

- 状态：已接受
- 日期：2026-09-15
- 决策者：chenmingboi（仓库作者，六项决策均委托本次提案的推荐方案）
- 相关：开发规范 §3.1、§4.6、§5.1、§8.1、§9.2、§9.5（新增）、§10.3、§10.6（新增）、§13.1、§13.6（新增）、§15.1、§16 阶段 I；ROADMAP 小项 I.1；ADR-0002（浏览器界面）、ADR-0004（检查点的存储位置与保留规则）

## 背景

阶段 H 已合并，阶段 I 是 ADR-0003 的 v3.0 范围里唯一一个改变“一次运行”这个基本单位的阶段。以下是 2026-09-15 的实现事实：

- `AgentLoop.run(task)` 每次都从零开始：新建 `MessageHistory`，`add_system(system_prompt)` 之后 `add_user(task)`，再新建 `RunState(original_task=task, ...)`。两次运行之间没有任何数据通路。
- `ContextManager.build` 依赖这个结构：它要求 `complete[:2]` 恰好是 system 消息与原始任务，并把 `history.messages[2:]` 切成交互组来裁剪。位置 0 和 1 是固定保留内容，永远不被裁掉。
- `MessageHistory.add_user` 要求用户消息跟在 system、assistant 或 tool 消息之后。**两条连续的用户消息是非法的**，所以“先放一条携带消息、再放一条任务消息”这种写法在现有历史不变量下不成立。
- 证据判定完全由程序拥有。`VerificationTracker` 只从**本次运行真实执行过**的工具结果记录证据，写进 `RunState.latest_verification`；`record_changed_file` 一旦被调用就把它清空。`finish_task` 工具自己不判定完成，它的返回值明说“AgentLoop must determine completion from injected local evidence”。
- 因此“验证证据不跨运行继承”今天是成立的——但它成立是因为**两次运行之间根本没有通路**，不是因为有哪条规则禁止它。一旦引入会话，这条性质就从“构造上的偶然”变成“需要被守住的不变量”。
- 运行产物都在工作区的 `.proofcoder/` 下：轨迹在 `.proofcoder/runs/<run_id>/trace.jsonl`，检查点在 `.proofcoder/checkpoints/<run_id>/`，命令审计在 `.proofcoder/runtime/commands/`。`safety/paths.py` 把 `.proofcoder` 登记为受保护路径，所有写工具拒绝写入，`secret_scan` 跳过它，它也在 `.gitignore` 里。
- 但**被允许的工作区脚本可以写 `.proofcoder/`**。文件工具的拒绝不是唯一通路，ADR-0004 已经接受了这个事实（检查点覆盖“被允许的工作区进程造成的变更”）。
- 浏览器界面已经用掉了“session”这个名字：`web/sessions.py` 里的 `RunSession` 和 `SessionManager` 指的是**内存中的一次浏览器运行**，不是跨运行的会话。服务重启即丢失，这是 ROADMAP“已知问题”里挂在阶段 I 下的一条。这个名字没有出现在任何用户可见的地方——HTTP 路由全部是 `/api/runs/...`。
- 开发规范 §10.3 把仓库内容视为不可信，§9.3 明确“未经处理的仓库文本不能提升为 system 指令”。上一次运行的 assistant 文本是模型读了仓库之后写的，属于同一类。
- 阶段 I 的退出条件有三条：后续运行能利用前序运行的结论但验证证据不跨运行继承；携带内容受上下文预算约束并经过与轨迹相同的脱敏；服务重启后会话能从持久化数据恢复。
- 开发规范 §16「v3.0 阶段通用规则」要求每个新增能力有真实模型评测 fixture 和重复运行数据。现有的评测流水线里，一个 attempt 恰好是一次运行：`materialize_fixture` 铺开工作区，跑一次 agent，再做一次独立验证。它目前无法表达“同一工作区里连着跑两次”。

## 决策

我们将按下表实现阶段 I 的跨运行会话。六个决策点都在“备选方案”中给出取舍，下表是推荐方案，六项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 携带什么 | 只携带程序生成的会话摘要，不携带原始消息历史；摘要分“程序事实”和“上一次运行的自述”两块，后者明确标注为模型主张 | 原样携带消息历史；只携带最终报告文本；让模型自己写交接摘要 |
| D2 证据如何不跨运行继承 | 会话数据只进入提示词，永远不进入 `RunState`；携带的摘要把上一次的验证标注为已过期；用行为反向测试锁定 | 依赖现状（无通路）；把上次验证藏起来不告诉模型；携带验证并加时效判断 |
| D3 携带内容放在哪里、如何受预算约束 | 作为 index 1 用户消息的定界前缀，运行开始前按确定性规则裁到硬上限（上下文预算的固定比例） | 追加进 system 消息；作为可被裁剪的交互组；不设上限只靠现有裁剪 |
| D4 会话存在哪里 | 工作区的 `.proofcoder/sessions/<session_id>/session.json`，严格 schema、全有或全无校验、逐字段长度上限 | 工作区外的用户级目录；存进浏览器 localStorage；只放内存 |
| D5 会话如何被选中 | 只能显式指定，没有隐式续接；不指定时行为与今天逐字节一致 | 自动续接同一工作区最近的会话；自动为每次运行建会话 |
| D6 命名冲突 | 把浏览器内部的 `RunSession`/`SessionManager` 改名，“会话”留给阶段 I 的跨运行概念 | 给阶段 I 的概念另起名字；两者共存靠模块前缀区分 |

这些规则新增开发规范 §9.5（跨运行会话上下文）、§10.6（会话数据的信任边界）和 §13.6（会话事件），修改 §4.6（CLI）、§5.1（目录结构）、§8.1（运行状态）和 §13.1（终端事件），并细化 §16 阶段 I 的实现清单与退出条件。第 2 节红线不变。

### D1 携带什么

会话携带的是**程序生成的摘要**，不是上一次运行的消息历史。摘要分成两块，边界在文本里就是可见的：

- **程序事实。** 上一次运行的 `run_id`、用户当时给的任务、终止原因、完成状态、程序记录的改动文件、程序统计的模型轮数与工具调用数，以及上一次的验证命令和退出码——后者带“已过期”标注，见 D2。这些全部来自 `RunState`，程序自己就能核对。
- **上一次运行的自述。** `finish_task` 的 `summary`、`limitations` 和 `blocked_reason`，逐字段截断后携带，并明确标注为模型的主张而不是已核实的事实。

第二块必须存在：退出条件说的是“后续运行能利用前序运行的**结论**”，而结论恰恰就是模型的自述。把它去掉，会话就只剩统计数字，起不到作用。它也必须被标注：这是模型写的文本，程序核对不了，它和程序事实混在一起就会被当成同一种东西。

不携带原始消息历史有三个理由，按重要性排列：

1. **它和证据判定直接冲突。** 上一次运行里 `run_command` 返回 `exit_code: 0` 的那条 tool 消息如果原样躺在上下文里，模型会合理地认为验证已经有了。程序仍然会拒绝把这次运行判为 `completed_verified`（`RunState` 是新的），但模型会反复调用 `finish_task` 并被反复驳回，把步数烧掉。程序生成的摘要可以把同一件事表达成“上次验证过，本次无效，需要重新取证”——既告诉了模型，又没有误导它。
2. **它没有上界。** 三次八步的运行，其历史在新任务的第一个 token 之前就会吃掉上下文预算。§9.2 的固定保留内容本来就在和预算竞争。
3. **它把不可信文本搬到了更前面的位置。** 按 §9.3，未经处理的仓库文本不能提升为 system 指令；上一次运行的 assistant 文本是模型读仓库之后写的，属于同一类。摘要是程序组装的，携带哪些字段、每个字段多长、怎么标注，都由程序决定。

这一条也和项目的核心特色一致：程序拥有证据，所以程序也拥有交接。把模型自己的话原样传下去，程序就审计不了自己携带了什么。

### D2 证据如何不跨运行继承

这是阶段 I 最容易实现错的地方，因为“顺手把状态一起带过去”是最自然的写法。三道措施：

- **单向。** 会话数据只有一个去处：组装成 D3 的那段文本，进入提示词。它不写 `RunState` 的任何字段，特别是 `latest_verification`、`last_modified_events` 和 `_changed_files`。`RunState` 仍然每次运行新建，仍然只由 `VerificationTracker` 从本次运行真实执行过的工具结果填充。
- **标注。** 携带的摘要里，上一次的验证命令带显式的“已过期”标记，并说明本次运行必须自己重新取得验证。把它藏起来是错的：模型知道上次用 `pytest -q` 验证过，本次就知道该跑什么，这是真实的收益；隐瞒它只会让模型多花几步去发现同一件事。
- **反向测试。** 一条离线测试：建一个会话，第一次运行取得验证并成功结束，第二次运行携带该会话、模型立刻调用 `finish_task` 且不执行任何命令——断言这次运行的 `completion_status` **不是** `completed_verified`。这条测试断言的是行为，不是字段，所以将来任何“顺手继承”的改法都会让它失败。

按同样的理由，检查点也不跨运行合并：每次运行仍然采集自己的基线，`.proofcoder/checkpoints/<run_id>` 的保留规则不变，回滚仍然是单次运行的回滚。会话不改变 ADR-0004 的任何一条。

### D3 携带内容放在哪里、如何受预算约束

摘要作为 **index 1 那条用户消息的定界前缀**，任务文本跟在它后面：

```text
[会话交接：...程序事实...  ...上一次运行的自述...]

<用户这次给的任务>
```

这个位置是唯一同时满足四个约束的位置：

- `MessageHistory` 不允许两条连续的用户消息，所以携带内容不能是独立的一条用户消息。
- `ContextManager.build` 要求 index 0 是 system、index 1 是任务，并只裁剪 `messages[2:]`，所以放在 index 1 里就自动属于 §9.2 的固定保留内容，不会在运行中途被裁掉——上一次运行的结论在第七步和第一步同样有用。
- 它是用户消息而不是 system 指令，符合 §9.3。
- `RunState.original_task` 仍然只存用户这次真正给的任务，`TASK` 事件因此不变；携带了什么由独立的 `SESSION` 事件记录。这样轨迹里“用户要求什么”和“程序带了什么”是两件分开的事。

预算约束是**运行开始前的硬上限**，不是运行中的裁剪：会话摘要在组装时就按确定性规则裁到上下文预算的固定比例（建议 1/8，可配置）。超出时按固定顺序丢弃——先丢最早那次运行的自述，再丢最早那次运行的整条记录，直到装得下；丢弃的条数写进 `SESSION` 事件。这样做的理由是，如果携带内容能随会话长度无限增长，一个长会话会让运行在第一次模型调用之前就抛 `ContextBudgetError`，会话越有用就越用不了。

摘要在写入提示词之前，经过与轨迹相同的脱敏（同一套 `sensitive_values`），并且会话文件本身也按脱敏后的内容存储，而不是存原文再在读取时脱敏。凭据不进入会话文件，和不进入轨迹是同一条规则。

### D4 会话存在哪里

会话存在工作区的 `.proofcoder/sessions/<session_id>/session.json`，`session_id` 与 `run_id` 同形（32 位小写十六进制），按同一套 `validate_run_id` 式的校验拒绝一切路径形态。

选工作区内而不是用户级目录，是为了让“会话属于一个工作区”这件事成为结构事实而不是约定——退出条件说的就是“同一工作区内”。它也和已有的三类运行产物（轨迹、检查点、命令审计）待在同一个地方，README、THREAT_MODEL 和规范里“ProofCoder 的本地状态都在 `.proofcoder/` 下”这句话继续成立。

**这里有一个必须写明的代价。** 文件工具拒绝写 `.proofcoder/`，但被允许的工作区脚本可以写它——ADR-0004 已经接受了这个事实。所以会话文件是可以被一个模型有权执行的脚本伪造的，而会话文件的内容会进入下一次运行的提示词。这不是一个新的威胁类别，它就是 §10.3 已经接受的“仓库内容不可信”，但它必须被当成那一类来处理，而不是被当成程序自己的数据：

- 会话文件里的模型自述部分，读出来之后按不可信内容对待：只作为用户消息的一部分出现，永远不提升为 system 指令，永远不作为任何判定的输入。
- 会话文件不携带任何会改变决定的东西：不含命令策略、不含审批状态、不含验证证据、不含路径授权。伪造一份会话文件的最坏结果是“模型读到一段误导性文字”，和仓库里放一个误导性的 README 是同一个量级。
- 每个字段有长度上限，条目数有上限，整文件有字节上限。伪造的文件撑不爆上下文，也撑不爆预算。
- schema 校验严格且全有或全无，和项目命令策略的加载一样：校验不过就整份不加载并报结构化错误，不做“能读多少算多少”。

这条会在 THREAT_MODEL 里作为独立一行记录，不藏在别的条目里。

### D5 会话如何被选中

会话只能显式指定。不指定 `--session` 时，`proofcoder run` 的行为与今天逐字节一致：新建历史、新建 `RunState`、不读也不写任何会话文件。

不做“自动续接同一工作区最近的会话”，理由和 D1 里策略文件必须被显式指名是同一个：**一次运行的输入应当是用户选定的。** 自动续接意味着用户在 A 任务之后跑一个无关的 B 任务时，B 会静默地继承 A 的上下文；用户要发现这一点，只能去读轨迹。显式指定的成本是多打一个参数，隐式续接的成本是一类没法一眼看出来的意外。

命令行入口：

```text
proofcoder session <list|show|end|delete> --workspace ./project [<session-id>]
proofcoder run --workspace ./project --session <session-id|new> "任务描述"
```

`--session new` 建一个新会话并在运行结束后写入第一条记录，`--session <id>` 续接，`session end` 把会话标记为结束（不再接受续接，但记录保留可查），`session delete` 删除。清理沿用检查点的形状：保留条数上限与总字节上限，在写入新记录前同步清理，且不删除进行中运行的会话。

浏览器入口：`/api/sessions` 系列路由与页面上的会话选择器，以及启动运行时可选的会话。服务重启后的恢复由 D4 的持久化文件提供——这同时把 ROADMAP“已知问题”里“服务重启后丢失进行中的会话”那条的一半解决掉：已完成的运行记录能恢复，进行中的运行仍然会随进程结束而中断，这一点会在文档里写明而不是含糊过去。

### D6 命名冲突

把 `web/sessions.py` 里的 `RunSession` 改名为 `BrowserRun`、`SessionManager` 改名为 `BrowserRunManager`，模块相应改名，“会话”这个词在代码和文档里只指阶段 I 的跨运行概念。

这不是约束变更，是实现卫生。做这个改名的理由是它现在几乎免费：这些名字没有出现在任何用户可见的地方（HTTP 路由全部是 `/api/runs/...`，页面脚本里一次 `session` 都没有），而阶段 I 之后同一个词会在同一个代码库里指两个不同生命周期的东西——一个是内存里活几十秒的运行，一个是磁盘上跨越数天的会话。

## 备选方案

**维持现状（不做阶段 I）。** 每次运行完全独立。优点是证据不跨运行继承这条性质不需要任何人守护，它由构造保证。缺点是同一个工作区里的连续任务无法利用前一次的结论，用户只能把上一次的结果手工粘进下一次的任务描述里——而手工粘贴恰恰是把模型自述当成事实的最坏形式，因为粘过去之后连“这是模型的主张”这个标注都没有了。ADR-0003 已经把多轮会话列入 v3.0 范围。

**原样携带消息历史（D1 的落选项）。** 把上一次运行的 `MessageHistory` 接到这一次前面。优点是实现最简单，模型看到的东西最完整。没有选是因为 D1 列出的三条：它让模型看到未过期标注的验证证据、它没有上界、它把不可信文本搬到了更前的位置。第一条是决定性的——它直接和项目的核心特色相抵。

**只携带最终报告文本（D1 的落选项）。** 只把上一次的 `finish_task` summary 带过去。优点是最小。没有选是因为它把程序事实和模型自述合并成了一段无法区分的文本：改动文件列表是程序记录的，摘要是模型写的，混在一起之后读者（和模型）没有办法知道哪部分是可核对的。

**让模型自己写交接摘要（D1 的落选项）。** 在运行结束时让模型额外产出一段“给下一次运行的交接”。优点是摘要质量可能更高。没有选是因为它多一次模型调用、引入一个新的失败模式（交接摘要本身可能为空或不合法），而且产出的仍然是模型主张——它没有解决区分问题，只是把同一个问题挪后了一步。

**依赖现状保证证据不继承（D2 的落选项）。** 什么都不做，因为 `RunState` 本来就是新建的。没有选是因为这条性质今天成立是构造上的偶然。将来某个人加一个“恢复运行状态”的便利方法，它会静默失效，而失效的表现是一次没有真实验证的运行被判为 `completed_verified`——这是这个项目最不能出的错。规则要写出来，并且要有一条断言行为的测试。

**把上次验证藏起来不告诉模型（D2 的落选项）。** 携带的摘要里不提上一次的验证。优点是模型不会被诱导去声称验证已有。没有选是因为它用隐瞒换安全，而安全并不来自隐瞒——来自 `RunState` 是新建的这个事实。隐瞒的代价是模型要重新发现该跑什么命令，白花步数。

**追加进 system 消息（D3 的落选项）。** 像 `_state_summary` 那样把携带内容拼到 system 消息末尾。优点是实现路径已经存在。没有选是因为携带内容含模型自述，而 §9.3 明确不能把未经处理的文本提升为 system 指令。

**作为可被裁剪的交互组（D3 的落选项）。** 把携带内容放在 `messages[2:]`，让现有裁剪逻辑处理。优点是不需要新的上限。没有选是因为上一次运行的结论在长运行的后半段比前半段更有用，而裁剪恰恰先丢最早的组——最该留的东西会最先被丢掉。

**工作区外的用户级目录（D4 的落选项）。** 把会话存到用户主目录下。优点是被允许的工作区脚本够不着它，D4 里那个代价就不存在了。没有选是因为：它要引入一个新的跨平台用户级状态目录（解析、权限、清理、与工作区的绑定关系），而现有三类运行产物都在工作区内、都面临同一个脚本写入风险、ADR-0004 已经接受了它；把会话单独挪出去只堵住四个洞里的一个，代价是打破“本地状态都在 `.proofcoder/` 下”这条现在处处成立的陈述。如果将来决定收紧，应当是四类产物一起搬，那会是另一篇 ADR。

**自动续接最近的会话（D5 的落选项）。** 见 D5：隐式继承的意外没法一眼看出来。

## 后果

- **正面：**
  - 同一工作区里的连续任务能利用前一次的结论，而且利用的是程序组装、可审计、带来源标注的摘要，不是手工粘贴的一段文本。
  - “验证证据不跨运行继承”从构造上的偶然变成写明的不变量，并有一条断言行为的反向测试守着它。
  - 携带内容有硬上限，长会话不会让运行在第一次模型调用之前就失败。
  - 浏览器界面的会话在服务重启后可恢复，ROADMAP 已知问题里的一条得到部分解决。
  - “会话”这个词在代码库里只有一个含义。
- **负面与新增风险：**
  - `.proofcoder/sessions/` 是可以被模型有权执行的工作区脚本伪造的，伪造内容会进入下一次运行的提示词。缓解见 D4，并在 THREAT_MODEL 中单列一行。这是已接受的 §10.3 威胁在新位置的一次出现，不是新类别。
  - 提示词里多了一段固定保留内容，挤占上下文预算。上限可配置，`SESSION` 事件记录实际占用和被丢弃的条数。
  - `AgentLoop.run` 多一个可选入参，`web/sessions.py` 的改名会碰到较多测试文件。两者都不改变既有行为。
  - 评测流水线需要能表达“同一工作区里连着跑两次”，这是 `eval_core`/`eval_runner` 的一次扩展，不是一次改写。
- **需要同步修改：** 开发规范 §4.6、§8.1、§9.2、§9.5（新增）、§10.6（新增）、§13.1、§13.6（新增）、§15.1、§16 阶段 I；`docs/ROADMAP.md` 的阶段 I 小项拆分；`CHANGELOG.md`。§5.1 的目录树在新模块实际存在时才改——合规检查 `documentation.spec_layout` 要求树中每个路径都存在，所以它属于实现落地的那一次变更。实现落地时还需要修改 `README.md`、`docs/DESIGN.md`、`docs/THREAT_MODEL.md` 和 `docs/COMPLIANCE.md`——按 §18.2，这些事实性文档只描述已合并的行为，因此不在本次仅含 ADR 与规范的变更中改动。

## 验证

- 反向测试（D2 的核心）：会话中第二次运行在不执行任何命令的情况下调用 `finish_task`，其 `completion_status` 不是 `completed_verified`。
- 会话摘要的组装是确定性的：同样的会话记录产生逐字节相同的携带文本；超出上限时丢弃顺序固定，且被丢弃的条数出现在 `SESSION` 事件里。
- 携带文本经过与轨迹相同的脱敏：把哨兵值放进上一次运行的自述，断言它既不出现在会话文件里，也不出现在组装后的提示词里。
- 会话文件的校验是全有或全无：字段缺失、类型不对、超长、条目过多、`session_id` 形态非法，各自有一条结构化错误，且任何一条都不产生“部分加载”的会话。
- 不指定 `--session` 时的行为与今天一致：现有的 golden 轨迹测试不需要重新生成。
- 浏览器：服务重启后已完成的运行记录能从持久化数据恢复；进行中的运行随进程结束而中断，这一点由测试固定下来而不是靠文档声明。
- 阶段 I 的评测：新增一个声明任务序列的 fixture，在同一工作区内连续运行，后一次运行能利用前一次的结论，且其成功判定仍然要求它自己的独立验证通过。
