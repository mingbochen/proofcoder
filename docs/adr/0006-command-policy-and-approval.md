# ADR-0006：项目级命令策略与人工审批

- 状态：已接受
- 日期：2026-09-15
- 决策者：chenmingboi（仓库作者，四项决策均委托本次提案的推荐方案）
- 相关：开发规范 §4.6、§7.6、§7.7、§10.3、§10.4、§13.1、§13.5、§15.1、§16 阶段 H、§17；ROADMAP 小项 H.1；ADR-0003（“MCP 暂缓，阶段 H 完成后重新评估”“同步主循环”两行）；ADR-0004

## 背景

阶段 F 与 G 已合并。命令能力是 ADR-0003 留给阶段 H 的最后一块写入面，也是唯一一处至今完全没有用户参与的安全决策。以下是 2026-09-15 的实现事实：

- 命令策略是写死在 `src/proofcoder/safety/commands.py` 里的可执行文件白名单：`python`（及其别名）、`pytest`、`ruff`、`git`、`g++`，其余一律 `COMMAND_BLOCKED`。用户无法为某个项目增加一条允许的命令。
- 判定不只看程序名。`git` 逐子命令区分读写，`pytest`、`ruff`、`g++` 逐选项校验路径与危险参数，`python` 只允许 `-m` 加固定模块集合。开发规范 §7.6 明确要求“同时检查可执行文件、子命令和危险参数，不能只按程序名放行”。
- 判定的结果只有两种：通过，或抛出 `CommandPolicyError`。没有“需要确认”这一档，`_GIT_WRITE_SUBCOMMANDS` 这样的高风险集合目前直接归入拒绝。
- `prepare_command` 返回的 `command_kind` 有双重身份：它既是轨迹里的分类，也是证据判定的输入。`verification.py` 的 `_VERIFICATION_COMMAND_KINDS` 只认 `test`、`build`、`static_check` 三类，`git_read` 不算证据。
- AgentLoop 是同步的，ADR-0003 要求阶段 H 的审批也在同步模型内解决。
- 浏览器界面已有一套可复用的机制：运行在后台线程里跑，事件经 `_SessionSink` 追加到会话，页面长轮询 `wait_for_events`，停止按钮通过 `request_cancel` 协作式取消。阶段 F.4 又加了“服务端签发摘要、确认时必须带回同一摘要”的绑定确认。
- 命令行已有一套可复用的机制：F.3 的回滚确认在 stdin 不是终端时拒绝执行而不是假设答案，并提供 `--yes` 供无人值守使用。
- 开发规范 §10.3 把仓库内容视为不可信：仓库里的文件、注释、测试和文件名都可能携带注入内容。
- 开发规范 §10.4 目前只有一段建议：`on-risk` 与 `never` 两种审批模式、默认拒绝、未知命令不得自动获得高权限。没有规定策略从哪里来、谁能改、等待审批时运行处于什么状态。
- 阶段 H 的退出条件之一是“新增至少一个非 Python 项目的评测 fixture”。这条排除了把项目策略写进 `pyproject.toml` 的做法。

## 决策

我们将按下表实现阶段 H 的命令策略与人工审批。四个决策点都在“备选方案”中给出取舍，下表是推荐方案，四项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 策略从哪里来 | 工作区内的 `proofcoder.toml`，但只有命令行显式指定才生效；运行开始前读取一次并冻结 | 发现即自动生效；写进 `pyproject.toml`；只用命令行参数逐条声明 |
| D2 “需要确认”怎么划 | 把现有的逐可执行文件校验器从“通过／拒绝”改成“允许／需确认／拒绝”三值 | 按程序名列白名单；只按危险参数特征判定 |
| D3 等待审批的语义 | 超时记为拒绝且运行继续；审批等待不计入运行时间预算，由独立上限约束；中断记为中断且命令不执行 | 超时记为中断；不设超时一直等；超时记为批准 |
| D4 批准与证据的关系 | 证据资格只由命令类别决定，与是否经过审批无关；项目策略必须显式声明类别，不猜测 | 经过审批的命令不计入证据；项目策略声明的命令一律不计入证据 |

这些规则改变开发规范 §10（重写 §10.4 为 §10.4.1–§10.4.6）和 §13（§13.1 增加一个终端事件，新增 §13.5），并细化 §16 阶段 H 的实现清单与退出条件。第 2 节红线不变。

### D1 策略从哪里来

项目级策略是工作区根目录下的 `proofcoder.toml`，用标准库 `tomllib` 读取，不引入新的运行依赖。它只能在默认拒绝的基础上**增加**允许的命令，不能删除 §10.4.5 的不可覆盖拒绝集合。

关键在于它默认不生效。**策略文件是仓库内容，而 §10.3 规定仓库内容不可信。** 一个克隆下来的仓库如果能凭自带的 `proofcoder.toml` 给自己授予命令权限，那么“默认拒绝”在任何敌意仓库面前都等于不存在——攻击者只需要把想执行的命令连同策略文件一起提交。因此：

- 策略只有在用户显式传入 `proofcoder run --command-policy <path>` 时才加载。不传就完全没有项目策略，行为与今天一致。
- 工作区里存在 `proofcoder.toml` 而用户没有传该参数时，发出一条警告事件说明检测到但未加载，以及如何加载。检测本身不读取其内容之外的任何东西，也不改变判定。
- 策略在第一次模型调用之前读取一次，解析成不可变对象后冻结。运行期间不重读。因此即使某次写入落到了策略文件上，本次运行的判定也不会改变。
- 策略文件路径登记为受保护路径，文件工具拒绝写入，与 `.env` 和 `.proofcoder` 同级。这是第二道防线，不是唯一一道。
- 加载成功时，把策略文件的 sha256 摘要写入轨迹，使事后审计能确定是哪一份策略在生效。摘要只覆盖文件内容，不包含路径以外的环境信息。

### D2 “需要确认”怎么划

判定保持单一入口，但结果从两值变为三值：`allow`、`confirm`、`deny`。

- `prepare_command` 现有的逐可执行文件校验链继续承担判定，只是把今天“高风险即拒绝”的分支改为返回 `confirm`。`git` 的写类子命令是第一批：它们今天被直接拒绝，改判后可以在用户确认下执行。
- 项目策略的每个条目声明可执行文件、允许的子命令、允许的选项、以及该条目的判定是 `allow` 还是 `confirm`。策略不能声明 `deny` 之外的任何东西来绕过 §10.4.5。
- 不引入“按程序名整体放行”的写法。策略条目必须能表达子命令与选项约束，这是 §7.6 已有的要求，三值化不放松它。
- 审批模式沿用 §10.4 已有的两档：`on-risk` 时 `confirm` 触发审批流程，`never` 时 `confirm` 直接按拒绝处理。评测运行一律使用 `never`，因此评测不会因等待人而阻塞。

### D3 等待审批的语义

审批在同步主循环内完成：工具执行到 `confirm` 判定时，发出审批请求事件并阻塞等待决定。

- **超时记为拒绝，运行继续。** 拒绝是一个普通的结构化工具结果，模型可以据此换一条路走；终止运行则把一次可恢复的犹豫变成不可恢复的失败。超时的方向也必须是“不产生副作用”那一侧。
- **审批等待不计入运行的时间预算**，而由独立的审批超时上限约束。`max_seconds` 的用途是防止 agent 自己跑飞，人在思考不是 agent 跑飞；若人的思考时间计入预算，一次被认真监督的运行反而会因为监督而死掉。等待时长单独记录在轨迹和运行结果里。
- **中断记为中断。** 等待期间收到中断时，运行以 `interrupted` 结束，待决的审批在轨迹中记为 `interrupted`，命令不执行。任何情况下都不得把未获答复的请求记为已批准。
- 命令行：在终端上提示完整的待批准命令（可执行文件、全部参数、cwd、超时）并读取答复。stdin 不是终端时按拒绝处理并说明原因，不假设答案——与 F.3 的回滚确认一致。
- 浏览器：审批请求作为事件渲染，决定通过一个新的接口回传，并复用 F.4 的摘要绑定——回传必须带上服务端随请求签发的摘要，摘要不匹配时拒绝该决定并返回当前待批准的请求。这样“批准”永远绑定在用户实际看到的那条命令上。
- 一次审批只对一次调用有效。不提供“记住这个命令”或“本次运行内始终允许”。

### D4 批准与证据的关系

证据资格由命令类别决定，与审批过程无关：

- 经过审批执行、且退出码表示成功的命令，与自动执行的同类命令具有相同的证据地位。审批决定的是“是否执行”，类别决定的是“算不算验证”。这两个轴正交。
- 项目策略的条目必须显式写出 `kind`，取值限定在现有的类别集合内。不从可执行文件名或参数猜测类别——`npm test` 是不是测试，只能由写策略的人回答。
- 策略不能凭空创造新的证据类别。`kind` 只能取 §7.7 与证据判定已经认识的值。

## 备选方案

### 维持现状

不提供项目策略，命令集合保持写死。优点是攻击面最小，也不需要任何新机制。没有选是因为它把 ProofCoder 限死在 Python 加 `g++` 的项目上：阶段 H 的退出条件明确要求一个非 Python 的评测 fixture，而任何非 Python 项目的测试命令今天都无法执行。

### D1：发现 `proofcoder.toml` 即自动加载

优点是零配置，符合大多数工具的习惯。没有选是因为它与 §10.3 直接冲突。策略文件是仓库内容，自动加载等于让仓库自行决定能在用户机器上运行什么命令；对一个克隆下来审阅的陌生仓库，这会把“默认拒绝”变成一句空话。显式加载只增加一次命令行参数的成本，却把这个决定交回给唯一有资格做它的人。

### D1：把策略写进 `pyproject.toml`

优点是 Python 项目不必新增文件。没有选有两个原因：阶段 H 的退出条件要求支持非 Python 项目，而那些项目没有 `pyproject.toml`；并且 `pyproject.toml` 是构建工具读取的文件，把安全策略混进去会让“哪些改动需要重新审阅”变得模糊。

### D1：只用命令行参数逐条声明允许的命令

优点是不读任何文件，攻击面最小。没有选是因为命令约束需要表达子命令与选项，塞进命令行参数会立刻变成一种简陋的嵌入式语法；而且策略无法随项目提交、无法被团队共享和审阅。文件加显式开关同时保留了可审阅性和明确授权。

### D2：按程序名列白名单

优点是实现简单，策略文件也最短。没有选是因为 §7.6 已经禁止它：只按程序名放行意味着允许 `git` 就同时允许了 `git push --force`。这一条不是实现细节，是既有的安全要求。

### D2：只按危险参数特征判定

优点是与具体程序解耦，新程序不需要新代码。没有选是因为危险性大量存在于子命令而不是参数里：`git status` 与 `git reset --hard` 的参数特征没有可靠差别，`npm run <script>` 的风险完全取决于脚本内容。特征判定可以作为补充，不能作为唯一依据。

### D3：超时记为中断

优点是语义强硬，绝不会出现“用户没看见就被拒了还继续跑”。没有选是因为拒绝已经保证了不产生副作用，而终止运行额外丢掉了已完成的工作和已采集的上下文。模型收到拒绝后换路线是常见且有价值的行为。

### D3：不设超时，一直等

优点是决定永远由人做出。没有选是因为它在无人值守场景下会让进程无限挂起，而 `never` 模式虽然覆盖了评测，却覆盖不了“用户开了 `on-risk` 然后离开”这种情况。独立上限保留了人做决定的充裕时间，又保证进程一定会结束。

### D3：超时记为批准

不可接受。默认方向必须是不产生副作用。此处列出只为说明它被明确排除。

### D4：经过审批的命令不计入验证证据

优点是证据链只包含全自动执行的命令，看起来更“干净”。没有选是因为它把两件无关的事绑在了一起，而且方向是错的：一条命令因为得到了人的确认反而失去证据资格，会让用户不得不避开审批路径才能让运行被判定为 verified，这正好奖励了错误的行为。

### D4：项目策略声明的命令一律不计入证据

优点是防止用户用策略文件伪造证据。没有选是因为这会让非 Python 项目永远无法达到 `completed_verified`——而支持这类项目正是阶段 H 的目的。要求显式声明 `kind` 已经把这个判断交给了人，并留下了书面记录。

## 后果

- **正面：** 非 Python 项目第一次可以被实际使用，阶段 H 的非 Python fixture 有了实现基础。今天被一刀切拒绝的高风险命令（`git` 写操作是最常见的一类）获得了一条有人把关的通路，而不是只能绕开。策略的加载、内容摘要、每一次审批请求与决定都进入轨迹，事后可以完整重建“当时允许了什么、谁批准了什么”。
- **负面与新增风险：** 引入了一个能扩大命令面的配置文件，这是本项目至今最接近“用户可自行放宽安全边界”的机制，其安全性依赖用户是否理解自己批准了什么。审批提示本身成为一个社会工程面：模型可以构造看起来无害的命令请求批准，因此 §10.4.5 的不可覆盖拒绝集合永远不得进入 `confirm`。审批等待不计入运行预算意味着单次运行的墙钟时间不再有统一上界，需要独立上限兜住。同步等待会在浏览器界面中占住那个运行的线程，界面必须清楚显示“正在等待你的决定”而不是显示成卡住。
- **需要同步修改：** 开发规范 §4.6、§7.6、§10.4、§13.1、§13.5、§15.1、§16 阶段 H、§17；ROADMAP 阶段 H 小项；CHANGELOG。实现落地时还需要修改 README、DESIGN 和 THREAT_MODEL——按 §18.2，这些事实性文档只描述已合并的行为，因此不在本次仅含 ADR 与规范的变更中改动。

## 验证

这个决策被正确实现的判据：

- 离线测试覆盖：未加载策略时行为与今天完全一致；工作区存在 `proofcoder.toml` 而未显式加载时只产生警告且判定不变；显式加载后新增命令按声明的类别与判定生效；策略试图放宽 §10.4.5 拒绝集合时加载失败而不是部分生效；运行期间改写策略文件不影响本次运行的判定；文件工具拒绝写入策略文件路径。
- 离线测试覆盖审批语义的四条出口：批准后执行、拒绝后不执行、超时按拒绝处理且运行继续、等待期间中断时运行以 `interrupted` 结束且命令不执行。四种情况都必须在轨迹中留下可区分的记录。
- 离线测试覆盖 `never` 模式下 `confirm` 判定不发起任何提示、直接按拒绝处理，据此保证评测不会阻塞。
- 离线测试覆盖浏览器审批的摘要绑定：摘要不匹配的决定被拒绝，并返回当前待批准的请求。
- 合规检查 `documentation.*` 继续通过，特别是规范 §7 工具表与 README 工具表的一致性不因本决策改变。
- 阶段 H 退出条件：新增至少一个非 Python 项目的评测 fixture，且该 fixture 的验证命令经由项目策略声明。
- 按 §16「v3.0 阶段通用规则」，阶段 H 还需要真实模型的重复运行数据，记入 `docs/EVAL_REPORT.md`。
