# ADR-0005：删除、移动与覆盖类文件工具

- 状态：已接受
- 日期：2026-09-14
- 决策者：chenmingboi（仓库作者）
- 相关：开发规范 §6、§7.4、§7.5、§10.5、§15.1、§16 阶段 G、§17；ROADMAP 小项 G.1；ADR-0003（“新建不覆盖、父目录必须存在；没有删除、移动、创建目录”一行）；ADR-0004

## 背景

阶段 F 已合并，回滚能力存在于 `main`。ADR-0003 把“放宽写入能力”的前提设为“先具备回滚”，这个前提现在成立。以下是 2026-09-14 的实现事实：

- 写入工具只有两个。`create_file` 在目标已存在时拒绝，且要求父目录已经存在；`replace_in_file` 一次调用只改一处文本，单文件上限 1 MiB。没有删除、移动、重命名或创建目录的工具。
- 因此模型无法完成一类常见任务：删除过时文件、重命名模块、把实现拆进新目录，或在一个文件里同时改多处而不发起多次调用。
- 回滚覆盖采集范围内的全部变更，包括被允许的工作区进程造成的写入。它能恢复被改动的文件、删除运行期间新出现的路径、重建被删除的文件，并按基线重建目录。
- 回滚有明确的覆盖缺口，且这些缺口恰好与删除类操作的风险重合：敏感路径只记元数据不记内容；超过 1 MiB 的文件只记元数据；默认忽略目录（`.git`、虚拟环境、`node_modules`、各类缓存）完全不在范围内；符号链接不跟随也不采集；工作区之外不覆盖。
- 检查点不是强制的。`proofcoder run --no-checkpoint` 可以在没有基线的情况下启动运行，此时任何写入都不可撤销。
- 工具风险等级只有 `read_only`、`write`、`execute` 三档，没有单独的“破坏性”档。
- 每个工具的参数由本地 JSON Schema 加本地验证器双重校验，未知字段一律拒绝。

## 决策

我们将按下表实现阶段 G 的文件工具扩展。四个决策点都在“备选方案”中给出取舍，下表的选项是提交审批时的推荐方案，四项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 删除的边界 | 单个文件或空目录，永不递归 | 递归删除目录；只允许删除文件 |
| D2 覆盖已有路径 | 默认拒绝，由显式参数逐次放开 | 有检查点就默认允许；新增一个总是覆盖的工具 |
| D3 多处修改的形状 | 一次调用携带多个精确替换，全部在内存校验后一次原子写入 | 统一 diff 补丁格式；按行号区间替换 |
| D4 没有检查点时 | 拒绝执行破坏性工具，非破坏性写入不受影响 | 一律可用；仅告警不拒绝 |

另有一处不构成取舍、按惯例直接决定：创建目录时一并创建缺失的父目录。逐层创建只会把同一件事拆成多次调用，而回滚按基线重建目录、并按最深优先移除运行期间新增的空目录，多层与单层的可撤销性完全相同。

### D1 删除的边界

`delete_path` 一次删除一个文件，或一个空目录：

- 目标必须位于工作区内，且经过与其它文件工具相同的路径、符号链接与敏感路径校验。
- 目标是非空目录时返回结构化错误，不递归删除。模型要清空一个目录，必须逐个删除其中的条目，每一次都单独出现在轨迹里。
- 目标是符号链接时删除链接本身，不跟随；目标不存在时返回 `PATH_NOT_FOUND`，不静默成功。
- 结果返回被删除路径的类型与字节数，不返回其内容。

### D2 覆盖已有路径

覆盖仍然默认拒绝，但可以逐次显式放开：

- `create_file` 增加 `overwrite` 参数，默认 `false`。为 `false` 时行为不变；为 `true` 时用同一套原子替换覆盖已有的普通文件，并返回覆盖前后的 diff。
- 目标是目录或符号链接时，无论 `overwrite` 取值一律拒绝。
- `move_path` 的目标路径必须不存在。需要覆盖时，模型先显式删除再移动，这样覆盖动作在轨迹里是两条可分别审计的记录。

### D3 多处修改的形状

`patch_file` 在一次调用里对同一个文件施加多处精确替换：

- 参数是一个有序的替换列表，每项包含 `old_text`、`new_text` 和可选的 `expected_replacements`，语义与 `replace_in_file` 完全一致。
- 全部替换按顺序在内存中施加并校验；任何一处零匹配或匹配次数不符，整次调用失败且文件不变。
- 全部通过后一次原子写入，返回合并后的 unified diff 与每项的实际替换次数。
- 不引入补丁文本格式、不做模糊匹配、不按行号定位。

### D4 没有检查点时

破坏性工具在没有检查点的运行中不可用：

- `delete_path`、`move_path`，以及 `overwrite=true` 的 `create_file`，在该次运行没有成功采集检查点时返回结构化错误并拒绝执行。
- `create_file`（不覆盖）、`replace_in_file`、`patch_file` 和 `make_directory` 不受影响：它们造成的改动要么是新增、要么是内容修改，回滚缺口不会把它们变成不可逆的破坏。
- 错误消息说明原因和恢复方向，即“这次运行没有检查点，去掉 `--no-checkpoint` 重新运行”。
- 工具是否可用由注册时的运行事实决定，不由模型的参数决定；模型不能通过任何参数绕过它。

## 备选方案

### D1 删除的边界

- **维持现状（没有删除工具）。** 不新增任何破坏面，但模型无法完成删除过时文件这类常规任务，阶段 G 也就无从谈起。未选。
- **允许递归删除目录。** 最贴近人类习惯，一次调用即可清理整棵子树。未选：递归删除是单次调用破坏面最大的操作，而回滚的覆盖缺口恰好落在最坏的位置——子树里若有超限文件、敏感文件或被忽略的目录，回滚无法恢复它们。一次误判就能造成不可撤销的损失，这与阶段 F 建立可恢复性的目的直接冲突。若将来确有需要，应在操作系统级隔离（阶段 L）之后另写 ADR 重新评估。
- **只允许删除文件，不允许删除目录。** 更保守，且空目录本身不含数据。未选：重命名或移动模块之后留下的空目录无法清理，会让工作区逐渐堆积无意义的残留；空目录的删除可由回滚按基线重建，风险与删除文件同级。

### D2 覆盖已有路径

- **维持现状（一律拒绝覆盖）。** 最安全。未选：模型要替换一个文件的全部内容时只能先删除再创建，比直接覆盖多一步破坏性操作，反而更危险。
- **有检查点就默认允许覆盖。** 参数最少，且检查点确实能恢复被覆盖的内容。未选：默认值决定绝大多数实际结果，把覆盖变成默认会让“意外整文件重写”从异常变成常态，而 `replace_in_file` 和 `patch_file` 已经覆盖了绝大多数修改场景。
- **新增一个总是覆盖的 `write_file` 工具。** 语义最清晰，两个工具各司其职。未选：两个近乎重复的工具会让模型在选择上出错，而错误的方向恰好是危险的那个；一个默认关闭的显式参数表达同样的意思，且在 schema 与轨迹里都能看到它被显式打开。

### D3 多处修改的形状

- **维持现状（多次调用 `replace_in_file`）。** 不新增协议面。未选：同一文件的多处修改会被拆成多轮模型调用，既浪费上下文预算，也让中间状态在磁盘上短暂存在——如果中途失败，文件会停在只改了一半的状态。
- **统一 diff 补丁格式。** 与人类工具链一致，表达力最强。未选：需要在本仓库实现补丁解析、上下文匹配与偏移容忍，这是一个很大的正确性面，也是补丁被静默错误施加的经典来源；本项目的红线要求解析逻辑自行实现，意味着这些缺陷全部由本仓库承担。
- **按行号区间替换。** 实现最简单。未选：行号在模型读取文件与发出调用之间极易失效，尤其是同一次调用里的多处修改会互相移动行号；精确文本匹配对这类漂移是免疫的。

### D4 没有检查点时

- **破坏性工具一律可用。** 实现最简单，且 `--no-checkpoint` 本来就是用户显式选择的。未选：ADR-0003 把回滚设为放宽写入能力的前提，如果没有检查点时破坏性工具照常可用，这个前提就只是文字。用户选择跳过检查点，不等于选择了在无保护状态下执行删除。
- **仅告警不拒绝。** 保留能力的同时提示风险。未选：告警出现在轨迹里，而破坏已经发生；对不可撤销的操作，事后告知没有价值。
- **没有检查点时整个运行就拒绝启动。** 最彻底。未选：这实际上等于取消 `--no-checkpoint`，而该开关对超出检查点上限的大型工作区是必要的逃生口；在那种工作区上做只读探索和普通编辑仍然合理。

## 后果

- **正面：**
  - 模型可以完成删除、重命名、建目录和同文件多处修改这类常规任务，不再需要绕路。
  - 每个破坏性操作都有对应的回滚覆盖，且在没有回滚保护时直接不可用——ADR-0003 的前提成为可执行的规则而不是声明。
  - 覆盖和删除都保持默认拒绝，放开的每一次都在参数和轨迹里可见。
- **负面与新增风险：**
  - 破坏面实质扩大。删除和覆盖能在一次调用中消灭内容，而回滚的缺口（敏感路径、超限文件、忽略目录、工作区之外）在这些操作上后果最重。
  - 逐个删除比递归删除慢，模型在清理大目录时会消耗更多轮次；这是刻意的取舍。
  - 工具数量从七个增加到十个，system prompt 与工具描述的维护成本上升，模型选错工具的空间也变大。
  - `patch_file` 与 `replace_in_file` 功能重叠，需要在工具描述中说明何时用哪个，否则模型可能总是选择表达力更强的那个。
- **需要同步修改：** 开发规范 §7（新增工具小节，随注册一并加入）、§10.5、§15.1、§16 阶段 G、§17；`docs/ROADMAP.md`；`CHANGELOG.md`。实现合并时还需更新 `README.md`、`docs/DESIGN.md`、`docs/THREAT_MODEL.md`、`docs/COMPLIANCE.md`。
