# ADR-0010：操作系统级命令隔离

- 状态：已接受
- 日期：2026-09-28
- 决策者：chenmingboi（仓库作者；2026-09-28 指示「一直往下尽可能的做」，七项决策均委托本次提案的推荐方案，可随时以新 ADR 推翻）
- 相关：开发规范 §4.6、§7.6、§10.4、§10.7（新增）、§13.1、§13.8（新增）、§15.1、§16 阶段 L、§17；ROADMAP 小项 L.1；ADR-0003（把完整操作系统沙箱移入范围）、ADR-0004（检查点只覆盖工作区）、ADR-0006（命令策略的三值判定）

## 背景

阶段 G 与 H 已合并，阶段 L 的依赖已满足。以下是 2026-09-28 的实现事实：

- `run_command` 用 `subprocess.Popen` 直接启动经策略判定的可执行文件：`shell=False`，工作目录限定在工作区，环境变量经过最小化过滤，POSIX 上以新会话启动以便超时后整组终止。除此之外，子进程拥有当前用户的全部权限。
- 被允许的命令几乎都会执行工作区代码：`python -m unittest` 导入工作区模块，`python script.py` 直接运行工作区脚本，`node --test` 同理。所以「命令被允许」在事实上等于「工作区代码以当前用户身份运行」。
- 因此一个被允许的工作区脚本今天可以：读取 `~/.ssh`、`~/.aws` 等主目录下的凭据；读取 `/proc/<ProofCoder 进程号>/environ`，其中包含提供方 API key——子进程环境过滤只过滤了子进程自己的环境，挡不住它去读父进程的；写工作区以外的任何当前用户可写路径；发起任意网络连接。THREAT_MODEL 的 TM-10、TM-26 与 §8 都把这一点记为剩余风险，README 的安全边界写明「ProofCoder 执行的是应用策略，而不是操作系统或内核沙箱」。
- 在当前开发容器（Linux 6.18）里用 ctypes 直接调用 Landlock 系统调用做了原型：ABI 版本 7；只把 `/usr`、`/lib`、`/lib64`、`/bin`、`/etc` 设为只读、工作区设为可读写之后，Python 解释器能正常启动并导入标准库；读写工作区外的文件、列出主目录、读取父进程的 `environ` 都返回 `PermissionError`；TCP 连接被拒绝。原型也暴露了一个细节：`tempfile` 在默认临时目录不可写时会静默退回到当前目录——也就是工作区。
- CI 在 `ubuntu-latest` 与 `windows-latest` 上运行。ProofCoder 的核心是同步的，但进程里有线程：命令输出读取线程、浏览器界面的服务线程与运行线程。
- 规范 §10.4 写明「当前版本不以 Docker 作为必需依赖」。

## 决策

### D1 机制：Linux Landlock，经 ctypes 直接调用

我们将在 Linux 上用 Landlock 隔离 `run_command` 启动的命令。Landlock 是内核自带的、无需特权的访问控制：一个进程可以给自己加上只能收紧、不能放宽、会被子进程继承的限制。三个系统调用（创建规则集、添加规则、对自身生效）用标准库 `ctypes` 调用，不引入任何依赖，也不依赖任何外部可执行文件。

隔离只作用于 `run_command` 启动的命令。ProofCoder 进程本身不受限——它要访问提供方、写轨迹、服务浏览器界面，而文件工具已经在进程内由路径策略约束。

### D2 执行方式：独立的执行包装进程

我们将不使用 `subprocess` 的 `preexec_fn`。Python 文档明确说明它在有线程的进程里不安全，而 ProofCoder 的进程里有线程。

取而代之的是一个执行包装：`run_command` 实际启动的是 `<当前解释器> -I -m proofcoder.sandbox_exec <配置> -- <原命令>`。包装进程依次设置资源限制、设置 `no_new_privs`、建立并应用 Landlock 规则集，然后用 `execve` 替换成原命令。`execve` 不改变进程号，所以超时后的整组终止、输出捕获和退出码都与今天相同。

**失败即关闭。** 包装进程在 `execve` 之前的任何一步失败，都以一个固定的退出码和固定的标记行退出，原命令不运行；`run_command` 把它识别为结构化错误 `SANDBOX_SETUP_FAILED`。不存在「隔离没建好就不隔离地跑」的路径。

### D3 文件系统规则

规则只能是允许列表。包装进程为以下位置添加允许规则，其余一律拒绝：

| 位置 | 权限 | 理由 |
|---|---|---|
| 工作区 | 读、写、执行、创建、删除 | 命令的工作对象 |
| 本条命令的私有临时目录 | 同上 | 位于工作区运行目录 `.proofcoder/tmp/` 下，命令结束后删除；`TMPDIR`、`TMP`、`TEMP` 指向它，以免 `tempfile` 退回工作区根目录 |
| `/usr`、`/lib`、`/lib32`、`/lib64`、`/bin`、`/sbin`、`/etc` | 只读与执行 | 解释器、动态链接库与系统配置；不存在的路径跳过 |
| 目标可执行文件的安装根目录 | 只读与执行 | 解析前后两个路径各算一次：可执行文件位于名为 `bin` 的目录时取其上一级，否则取其所在目录。覆盖 uv、pyenv、nvm 安装在主目录下的解释器及其标准库，以及虚拟环境的 `pyvenv.cfg` |
| `/dev/null` | 读写 | |
| `/dev/zero`、`/dev/random`、`/dev/urandom` | 只读 | |
| `/proc/<本进程号>` | 只读 | 包装进程在 `execve` 前以自己的进程号添加，`execve` 后进程号不变；其他进程的 `/proc` 条目——包括 ProofCoder 自身的 `environ`——不可读 |
| 用户以 `--sandbox-read <路径>` 追加的路径 | 只读与执行 | 可重复。用于放在工作区之外、命令需要读取的依赖，例如工作区外的虚拟环境。只能由用户在命令行给出，不能来自仓库内容 |

「工作区以外的宿主文件不可读写」据此精确表述为：工作区之外，只有上表列出的只读位置可读，没有任何位置可写；用户主目录（除了恰好落在上表中的路径）不可读。

Landlock 规则只增不减，无法在允许的工作区之内再拒绝一个子目录。所以工作区运行目录 `.proofcoder/`（轨迹、检查点、会话）对命令仍然可写，TM-33 记录的会话伪造风险不因本 ADR 改变。

### D4 网络与作用域

Landlock ABI ≥ 4 时，默认拒绝所有 TCP 的 `bind` 与 `connect`。`--sandbox-network allow` 可以放开 TCP，供需要本地服务的测试使用；它只能由用户在命令行给出。

ABI ≥ 6 时，额外限定抽象 Unix 套接字与信号的作用域：命令不能连接沙箱外进程的抽象套接字，也不能向沙箱外的进程发信号。

Landlock 不管辖 UDP 与路径型 Unix 套接字的连接。这两项写入 THREAT_MODEL 作为剩余风险，不假装已被隔离。

### D5 资源限制

包装进程在应用 Landlock 之前设置：

- `RLIMIT_CORE` 为 0：不留核心转储，转储可能含有内存里的敏感值。
- `RLIMIT_FSIZE` 为 1 GiB：单个文件不能被写到超过这个大小。
- `RLIMIT_NOFILE` 的软限制不超过 4096。
- `RLIMIT_CPU` 为命令超时加 5 秒：墙钟超时之外的第二道上限。

不设置 `RLIMIT_AS`：V8 等运行时预留的虚拟地址空间远大于实际使用，按地址空间限制会让 `node` 在正常工作时启动失败。不设置 `RLIMIT_NPROC`：它按用户计数，会把用户在别处运行的进程也算进去。内存与进程数的耗尽因此只由超时和整组终止约束，写入 THREAT_MODEL。

### D6 模式与降级

我们将提供三种模式，由 `proofcoder run --sandbox <auto|required|off>` 选择，评测与浏览器界面提供同一选项，默认 `auto`：

- `auto`：隔离可用就启用；不可用时命令按阶段 L 之前的方式运行。
- `required`：隔离必须可用，并且能满足用户要求的每一项限制（例如要求拒绝网络而内核 ABI < 4 即不满足）；否则**运行不开始**，在联系提供方之前以配置错误结束。
- `off`：不隔离，与阶段 L 之前一致。

可用性在运行开始前探测一次，结论在整次运行中不变，并通过三处明确呈现：每次运行的 `SANDBOX` 轨迹事件、终端的一行提示、`doctor` 的一项检查。状态取值为 `enforced`（文件系统与所要求的网络限制都生效）、`partial`（文件系统生效，网络限制因 ABI 不足未生效）、`unavailable`（Linux 上探测失败，附原因）、`unsupported`（非 Linux 平台）与 `off`（用户关闭）。

**为什么默认是 `auto` 而不是 `required`，以及它为什么仍然是默认安全的。** 默认 `required` 会让所有 Windows 与 macOS 安装、以及未启用 Landlock 的 Linux 内核上的每一条命令都无法运行——命令不能运行，验证就无法产生，`completed_verified` 在这些平台上永远不可达。`auto` 在隔离不可用时的行为，恰好是阶段 L 之前全部平台上的行为：默认拒绝的命令策略、审批、检查点都不变，所以 `auto` 不会让任何平台比今天更不安全，只会在能加的地方加一层。它的「安全」由三条规则保证：降级在运行开始前决定一次，从不在命令执行中途发生；任何低于完全隔离的状态都被明确记录，从不静默；隔离一旦判定可用，单条命令的建立失败就是失败（D2），不回退为不隔离。

### D7 与证据判定的关系

隔离不改变证据判定。被 Landlock 拒绝的访问在命令内部表现为普通的权限错误，命令以它自己的退出码结束，这个退出码按 §10.4.6 与 §7.7 的既有规则参与判定。验证证据记录的命令身份仍是用户看到的原命令，不包含包装进程。每条命令的工具结果与轨迹事件记录它是否在隔离中运行。

### 非 Linux 平台

本阶段不实现 Windows 与 macOS 上的隔离，状态记为 `unsupported`。Windows 的 AppContainer 需要为工作区与每个依赖目录维护 ACL，且许多工具链在其中无法运行；作业对象（Job Object）只能限制资源，不能限制文件访问；Windows Sandbox 是虚拟机。macOS 的 `sandbox-exec` 已被系统标记为弃用。这些平台上的剩余风险——被允许的工作区脚本拥有当前用户的全部权限——在 THREAT_MODEL 中保持原有描述并单列说明。

## 备选方案

**维持现状（不做阶段 L）。** 优点是没有新代码，也没有新的失败模式。缺点是阶段 L 的退出条件无法满足，且 `/proc/<pid>/environ` 让任何被允许的工作区脚本都能读到提供方 key，这一点今天没有任何控制。

**Docker 或 Podman 容器。** 优点是隔离更完整（文件系统、网络、进程、资源都能管），跨 Linux 发行版行为一致。没有选是因为它要求守护进程或额外安装，与 §10.4「不以 Docker 作为必需依赖」冲突；容器内要重建与宿主一致的工具链，否则 `python` 与 `node` 的版本会与用户的不同；Windows 上还要虚拟化。

**bubblewrap 或 firejail。** 优点是成熟、支持挂载命名空间，隔离面比 Landlock 更完整。没有选是因为它们是操作者自备的外部可执行文件，与 ripgrep 同属供应链边界，而且往往没有安装；bubblewrap 依赖非特权用户命名空间，而 Ubuntu 24.04 默认用 AppArmor 限制了非特权用户命名空间。

**直接调用 `unshare` 建立用户与挂载命名空间。** 没有选，理由同上：非特权用户命名空间在主流发行版上越来越多地被默认限制，可用性不如 Landlock。

**只用 seccomp-bpf。** 优点是能限制系统调用。没有选是因为它按系统调用而不是按路径过滤，无法表达「只允许读这些目录」；与 Landlock 叠加是可能的后续工作，但不是本阶段退出条件所需。

**第三方 `landlock` Python 包。** 优点是省去手写 ctypes 结构。没有选是因为它是新的运行时依赖，而所需的只是三个系统调用与三个结构体。

**`preexec_fn` 在子进程里应用 Landlock（D2 的落选项）。** 优点是不需要额外的 Python 启动。没有选是因为它在有线程的进程里不安全。每条命令多一次解释器启动（约几十毫秒）是可以接受的代价。

**把整个 ProofCoder 进程放进 Landlock。** 没有选是因为 ProofCoder 本身需要网络与工作区外的读取（配置、依赖），而 Landlock 一旦生效就无法撤销，浏览器界面还要在一个进程里服务多次运行。

**默认 `required`（D6 的落选项）。** 见 D6。

**隔离不可用时要求逐条审批（D6 的落选项）。** 优点是用户会注意到。没有选是因为评测以 `never` 模式运行，这会让所有非 Linux 平台上的评测命令全部被拒绝；而审批请求的内容也无法说明「这条命令没有被隔离」之外的任何新信息，这一点已经由运行开始时的事件与提示说明。

## 后果

- **正面：**
  - 在支持的 Linux 上，被允许的工作区脚本第一次不能读取主目录里的凭据、不能读取 ProofCoder 进程的环境变量、不能写工作区以外的任何地方、默认不能发起 TCP 连接。
  - 没有新增运行时依赖，也没有新增外部可执行文件。
  - 隔离状态在每次运行中都可审计。
- **负面与新增风险：**
  - 每条命令多一次 Python 解释器启动。
  - 依赖工作区之外文件的命令在隔离下会失败，例如使用工作区外虚拟环境、读取 `~/.gitconfig` 或主目录缓存的工具。缓解是 `--sandbox-read` 与 `--sandbox off`，并在 README 说明。
  - `/etc` 整体可读。它的内容按设计对所有用户可读，但不同主机上可能包含站点特定的信息。
  - UDP、路径型 Unix 套接字、内存与进程数不在隔离范围内。
  - 工作区运行目录对命令仍可写（Landlock 无法在允许的目录里再拒绝子目录）。
  - Landlock 在不同内核上的 ABI 不同，行为差异通过 `partial` 状态呈现，而不是被抹平。
  - Windows 与 macOS 上没有任何变化。
- **需要同步修改：** 开发规范 §4.6、§7.6、§10.4、§10.7（新增）、§13.1、§13.8（新增）、§15.1、§16 阶段 L、§17；`docs/ROADMAP.md` 的阶段 L 小项拆分；`CHANGELOG.md`。实现落地时还需要修改 §5.1 目录树、`README.md`（安全边界与新选项）、`docs/DESIGN.md`、`docs/THREAT_MODEL.md`（TM-10、TM-26、§8 的重新评估与新增行）和 `docs/COMPLIANCE.md`。

## 验证

- 在 Landlock 可用的 Linux 上：被允许的工作区脚本读取工作区外的文件、写工作区外的路径、列出主目录、读取父进程的 `environ` 都失败；读写工作区与私有临时目录成功；ABI ≥ 4 时 TCP 连接失败，`--sandbox-network allow` 时成功。
- 包装进程建立隔离失败时，原命令不运行，工具结果为 `SANDBOX_SETUP_FAILED`。
- `required` 模式在隔离不可用或不能满足所要求的限制时，运行在联系提供方之前结束。
- `auto` 模式在隔离不可用时，命令的行为与 `off` 一致，且 `SANDBOX` 事件记录 `unavailable` 或 `unsupported` 及原因。
- 每次运行恰好产生一个 `SANDBOX` 事件；`off` 模式也产生，以便审计能区分「用户关闭」与「平台不支持」。
- 验证证据中的命令身份不含包装进程；隔离中运行的测试命令通过时，完成状态仍可达 `completed_verified`。
- 非 Linux 平台上相关测试跳过，且 THREAT_MODEL 写明该平台的限制。
