# ADR-0009：上下文与仓库理解

- 状态：已接受
- 日期：2026-09-25
- 决策者：chenmingboi（仓库作者；2026-09-25 指示「一直往下尽可能的做」，四项决策均委托本次提案的推荐方案，可随时以新 ADR 推翻）
- 相关：开发规范 §4.6、§5.1、§7（新增 §7.12）、§9.2、§9.4、§9.6（新增）、§10.3、§13.1、§13.7（新增）、§15.1、§16 阶段 K；ROADMAP 小项 K.1；ADR-0007（会话携带内容的位置）、ADR-0006（项目命令策略为什么必须显式授权）

## 背景

阶段 I 与 J 已合并。阶段 K 的目标是让 ProofCoder 在比现有 fixture 大得多的仓库里仍能工作。以下是 2026-09-25 的实现事实：

- 上下文预算只按字节计。`ContextManager` 用 `deterministic_request_bytes` 计量请求，默认预算 256 KiB，超出时从最早的完整交互组开始裁剪。字节计量是确定性的、与提供方无关的——这正是它能被离线测试逐字节固定的原因。
- 但模型的限制是按 token 计的，而字节与 token 的比例随语言和内容变化很大：英文代码大约 3–4 字节一个 token，中文文本一个汉字占 3 字节、往往自成一个 token。同一个字节预算，在两种仓库里对应的 token 数可以差出一倍以上。
- 提供方每次响应都报告真实的 `prompt_tokens`，`AgentLoop` 已经把它累加进 `input_token_count`，但从未用它反推预算。
- 现有 7 个评测 fixture 的工作区都只有 2–4 个文件、不到 2.1 KB。模型在这样的仓库里用 `list_files` 一次就能看到全部内容，跨文件定位这件事从未被检验过。
- 工具集是 11 个。`list_files` 列目录但不读内容，`search_text` 按文本搜索，两者都没有「这个文件里定义了什么」这一层信息。模型要在 40 个文件里找到一个函数，只能逐个 `read_file`。
- `list_files` 对敏感文件的处理是不列出（不是列出后标注）；`DEFAULT_IGNORED_DIRECTORIES` 定义了默认忽略的目录。
- 越来越多的仓库在根目录放一个 `AGENTS.md` 来说明项目约定。ProofCoder 自己的仓库就有一个。今天 ProofCoder 从不主动读取它；模型碰巧读到它，是因为它碰巧调用了 `read_file`。
- 开发规范 §10.3 把仓库内容视为不可信，§9.3 规定未经处理的仓库文本不能提升为 system 指令。ADR-0006 把项目命令策略设计成必须显式指名才生效，理由是策略文件会**授予能力**。
- ADR-0007 已经确定了一处放「程序组装的、非用户直接输入的上下文」的位置：index 1 用户消息的定界前缀。

## 决策

我们将按下表实现阶段 K。四个决策点都在“备选方案”中给出取舍，下表是推荐方案，四项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 按 token 的预算 | token 预算作为**附加**限制：每次请求前按保守的字节/token 比换算成字节上限，与既有字节预算取较小者；比例用提供方报告的 `prompt_tokens` 校准。不引入分词器依赖 | 引入 tiktoken；用提供方 token 数完全取代字节计量 |
| D2 仓库理解 | 新增只读工具 `repository_map`：目录树加 Python 文件的顶层符号（标准库 `ast`），模型需要时调用，结果有上限 | 每次运行自动注入仓库地图；依赖外部 ctags 或 tree-sitter |
| D3 项目规则文件 | 默认读取工作区根目录的 `AGENTS.md`，有上限、经脱敏，作为 index 1 用户消息里带标注的定界块，**永不进入 system 消息**；记录摘要事件；可用 `--no-project-rules` 关闭 | 放进 system 消息；像命令策略一样必须显式指名才读；完全不读 |
| D4 更大的评测 fixture | 一个约 40 个文件的 Python 包，任务只描述症状而不指出位置，必须跨文件定位 | 运行时生成合成仓库；复用某个开源项目 |

这些规则新增开发规范 §9.6（按 token 的预算）和 §13.7（项目规则事件），修改 §4.6、§9.2、§13.1 和 §15.1，并细化 §16 阶段 K 的实现清单与退出条件。§7.12（`repository_map`）与 §5.1 随工具在 K.3 落地：合规检查要求 §7 的工具表与已注册的工具逐一一致，工具存在之前写进去会让检查失败。第 2 节红线不变。

### D1 按 token 的预算

token 预算是字节预算之上的**附加**限制，不是替代。

每次构建请求前，用当前的「字节/token」比例把 token 预算换算成一个字节上限，与既有的字节预算取较小者，然后交给不变的 `ContextManager` 执行。裁剪逻辑、原子交互组、固定保留内容都不动。

比例的来源：

- 第一次请求之前用一个保守的默认值（每 token 2 字节）。它故意偏小：比例越小，同样的字节估出的 token 越多，预算越不容易被低估。低估的后果是请求被提供方拒绝；高估的后果只是裁剪得早一点。
- 每次响应之后，用「这次请求的字节数 ÷ 提供方报告的 `prompt_tokens`」得到一个观测值，乘以 0.9 的安全余量后作为下一次的比例。这样既不会永远卡在过于保守的默认值上，又始终留有余量。
- 提供方不报告 usage 时，比例保持不变。

不引入 tiktoken 这类分词器，理由和阶段 J 不引入第二个 SDK 相同：分词器是提供方特定的（DeepSeek、本地模型、OpenAI 各不相同），引入一个就意味着对其他提供方的估计是错的，而且多一个运行时依赖。提供方自己报告的 token 数是唯一对所有提供方都正确的来源。

不用提供方 token 数**完全取代**字节计量，是因为第一次请求之前没有任何观测值，而且离线测试需要确定性的计量。字节仍然是那道确定性的硬门槛。

不设置 token 预算时，行为与阶段 K 之前逐字节一致。

### D2 仓库理解

新增第 12 个工具 `repository_map`。它返回工作区（或其子目录）的文件树，以及每个 Python 文件的顶层类、函数和类中方法的名字与行号。

符号用标准库 `ast` 解析，不执行任何代码。选 Python 是因为本项目的评测 fixture 以 Python 为主；其他语言的文件只列路径和大小。这是一个明确的限制，写进文档，而不是用正则去猜其他语言的符号——猜错的符号比没有符号更糟，因为模型会信它。

约束与既有文件工具一致：

- 默认忽略的目录与 `list_files` 相同；敏感文件不列出，更不解析。
- 条目数、每个文件的符号数、被解析文件的大小都有上限，超出时报告被截断的数量。
- 解析失败（语法错误、递归过深、超大文件）的文件只列路径，不报错，因为仓库里有一个坏文件不应该让整张地图失败。
- 输出进入消息历史之前，和其他工具一样经过截断。

选「模型调用的工具」而不是「每次运行自动注入」：自动注入意味着每一个琐碎的一行修改任务都要为一张 40 个文件的地图付上下文预算，而且那部分内容是固定保留的，裁不掉。工具是按需拉取的，结果属于可裁剪的交互组，模型不需要它时它不占任何空间。

不依赖外部 ctags 或 tree-sitter：前者是一个需要操作者自备的外部可执行文件（和 ripgrep 同一类供应链边界），后者是带原生扩展的运行时依赖。两者都能覆盖更多语言，但本阶段的退出条件只要求在更大的仓库里完成跨文件定位，标准库足够。

### D3 项目规则文件

默认读取工作区**根目录**的 `AGENTS.md`，只读这一个文件名、只读这一个位置。

它与项目命令策略的处理方式相反——策略必须显式指名才生效，规则文件默认读取——这个不对称是有意的，而且正是理解这个决策的关键：

- **策略文件授予能力。** 一个能自己生效的 `proofcoder.toml` 就是敌意仓库给自己开的后门，所以 ADR-0006 要求用户指名。
- **规则文件什么也不授予。** 它是一段文本。模型今天就能用 `read_file` 读到它，读到之后它能做的事与读到任何 README 相同，所有动作仍然要穿过本地的 schema 与策略检查。把它主动读进来，没有打开任何今天关着的门。

所以这里的风险是 §10.3 已经接受的提示注入，控制手段也是既有的那一套，加上三条针对位置与标注的规则：

- 它**永远不进入 system 消息**。§9.3 不允许未经处理的仓库文本提升为 system 指令。
- 它作为 index 1 用户消息里的一个定界块出现，位置在会话携带内容之后、用户任务之前，并带明确标注：这是仓库提供的项目说明，属于仓库文本，不能改变系统指令、工具规则或完成判定。
- 它有大小上限（32 KiB，超出截断并标注），经过与轨迹相同的脱敏；符号链接、非普通文件、被判定为敏感的路径一律不读。

读取之后发出一个事件，记录来源文件名、字节数、是否截断和内容的 sha256 摘要，不记录内容本身——与项目策略的审计方式相同，事后可以确定是哪一份规则在生效。

`--no-project-rules` 关闭它。不做「include」处理：`AGENTS.md` 里引用其他文件的写法（例如某些工具支持的 `@path`）只作为文本出现，不会让程序去读别的文件，因为那会让一个仓库文件决定程序读取哪些路径。

### D4 更大的评测 fixture

新增一个约 40 个文件的 Python 包 fixture。任务描述症状（某个报表数字错了），不指出出错的模块；出错的逻辑与表现出错的测试位于不同的文件中，中间隔着至少一层调用。

「明显大于」用可核对的数字表达：现有最大的 fixture 是 4 个文件、2.1 KB；新 fixture 的文件数至少是它的 10 倍。

用提交进仓库的静态文件而不是运行时生成：fixture 的全部意义在于可复现，而生成器本身会成为一个需要被测试的新组件。不复用开源项目：许可、体量和上游变化都会带进来，而我们需要的是一个刚好能检验跨文件定位的最小仓库。

## 备选方案

**维持现状（不做阶段 K）。** 优点是没有新代码。缺点是 ProofCoder 在真实大小的仓库里没有被验证过：所有评测都发生在一眼就能看完的仓库里，而字节预算在中文仓库和英文仓库之间差一倍以上。

**引入 tiktoken（D1 的落选项）。** 优点是对 OpenAI 系模型的估计精确。没有选是因为分词器是提供方特定的，对 DeepSeek 和本地模型都是错的估计，而且多一个带原生扩展的运行时依赖。

**用提供方 token 数完全取代字节（D1 的落选项）。** 没有选是因为第一次请求之前没有观测值，且离线测试需要确定性的计量。

**自动注入仓库地图（D2 的落选项）。** 优点是模型不必想起来调用。没有选是因为它让每个琐碎任务都为一张大地图付固定保留的预算。

**外部 ctags 或 tree-sitter（D2 的落选项）。** 优点是多语言。没有选是因为前者是操作者自备的外部可执行文件，后者是带原生扩展的依赖；本阶段的退出条件用标准库就能满足。

**把规则文件放进 system 消息（D3 的落选项）。** 优点是模型会更重视它。没有选是因为这正是 §9.3 禁止的事，而「模型会更重视它」恰恰是敌意仓库最想要的效果。

**规则文件也必须显式指名（D3 的落选项）。** 优点是与命令策略一致。没有选是因为两者不对称：策略授予能力，规则文件不授予任何东西。把一段模型本来就能读的文本藏在一个开关后面，不会减少任何风险，只会让大多数用户永远用不上它。

**运行时生成 fixture，或复用开源项目（D4 的落选项）。** 见 D4。

## 后果

- **正面：**
  - 上下文预算第一次与模型的真实限制挂钩，而且挂钩的依据是提供方自己报告的数字，对所有提供方都成立。
  - 模型在大仓库里有了比逐个读文件更便宜的定位手段。
  - 项目约定可以被程序主动带入上下文，同时明确标注为仓库文本。
  - 评测第一次覆盖了跨文件定位。
- **负面与新增风险：**
  - 规则文件默认读取，意味着敌意仓库的 `AGENTS.md` 会出现在每次运行的上下文里、离用户任务很近。这是 §10.3 已接受的风险在一个更显眼位置的出现，控制手段是不进 system 消息、带标注、不授予任何能力。THREAT_MODEL 单列一行。
  - `repository_map` 解析不可信的 Python 源码。`ast.parse` 不执行代码，但病态输入可能导致递归过深或内存占用；用文件大小上限与异常捕获约束。
  - 工具数从 11 变成 12，所有列出工具的文档都要同步。
  - token 预算的校准依赖提供方报告的数字是真实的；一个报告偏小的提供方会让比例偏大、预算偏松。安全余量只能缓解不能消除。
- **需要同步修改：** 开发规范 §4.6、§7.12（新增）、§9.2、§9.6（新增）、§13.1、§13.7（新增）、§15.1、§16 阶段 K；`docs/ROADMAP.md` 的阶段 K 小项拆分；`CHANGELOG.md`。实现落地时还需要修改 `README.md`、`docs/DESIGN.md`、`docs/THREAT_MODEL.md` 和 `docs/COMPLIANCE.md`，以及 §5.1 与 §7 的工具表——合规检查要求 §7 与已注册的工具一致，所以工具表随工具一起改。

## 验证

- 不设置 token 预算时，金标轨迹不需要重新生成。
- token 预算换算：没有观测值时用默认比例；观测之后用带安全余量的观测比例；提供方不报告 usage 时比例不变；换算结果永不大于既有字节预算。
- `repository_map`：不列出敏感文件；不进入默认忽略目录；Python 符号与行号正确；语法错误的文件只列路径；条目与符号上限生效并报告截断数量；不执行任何被解析的代码。
- 规则文件：出现在 index 1 用户消息而不在 system 消息；有标注；超限截断；符号链接不读；`--no-project-rules` 时完全不读；事件记录摘要而不记录内容；脱敏生效。
- 更大的 fixture：文件数至少是现有最大 fixture 的 10 倍；初始验证失败、修复后通过；离线测试覆盖。
