# ADR-0004：工作区检查点与回滚

- 状态：已接受
- 日期：2026-09-13
- 决策者：chenmingboi（仓库作者）
- 相关：开发规范 §2.3、§7.6、§10.2、§10.5、§13、§15.1、§16 阶段 F、§17；ROADMAP 小项 F.1；ADR-0003（“不自动提交 Git”一行改为运行前检查点）

## 背景

阶段 F 要让“任何写入都能回滚到运行前的状态”成立。以下是 2026-09-13 的实现事实，它们决定了可选的方案空间：

- 内置写入工具只有 `create_file`（目标已存在时拒绝）和 `replace_in_file`（精确替换），单文件上限 1 MiB，写入方式是同目录临时文件加原子替换，替换前用 `FileSnapshot` 复核设备号、inode、权限位、大小、mtime/ctime 和内容摘要。写入之后没有任何撤销能力：运行被中断、预算耗尽或内部错误终止后，已改动的文件保持改动后的内容。
- 命令策略默认拒绝，但允许 `python <工作区脚本>.py`、`pytest`、`ruff check`、`ruff format --check`、`g++` 和只读 `git` 子命令。其中工作区脚本和 `g++ -o` 以当前用户权限运行，可以写入文件工具规则之外的任何路径，包括工作区之外；README 的“Security Boundaries”已经声明这一点。阶段 L 之前没有操作系统级隔离。
- 运行产物写在工作区内的 `.proofcoder/runs/<run_id>/trace.jsonl`，目录以 0o700 创建，`run_id` 是 32 位小写十六进制。`.proofcoder` 同时出现在本仓库的 `.gitignore` 和 `list_files`、`search_text` 的默认忽略目录中。目前没有任何保留期或清理逻辑，运行目录只增不减。
- `read_file`、`create_file`、`replace_in_file` 通过 `is_sensitive_path` 拒绝 `.env`、`.env.*`、私钥、证书、`credentials.json` 等路径；工作区脚本不受这条限制。
- 开发规范 §16 阶段 F 要求回滚覆盖内置工具和被允许的工作区进程造成的变更，并要求检查点不得把凭据内容写入运行产物。
- ADR-0003 规定：放宽写入和命令能力之前必须先具备回滚能力，阶段 G（删除、移动、覆盖）和阶段 H（更宽的命令策略与人工审批）以阶段 F 为前提。
- 默认测试必须离线且确定，CI 同时在 ubuntu-latest 和 windows-latest 上运行。运行依赖限于 `openai` 和 `rich`，其余功能优先用标准库实现。

## 决策

我们将按下表实现阶段 F 的检查点与回滚。四个决策点都在“备选方案”中给出了完整的取舍，下表的选项是提交审批时的推荐方案，四项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 存储方式 | 运行开始时采集内容寻址的影子副本，纯标准库实现 | 影子 Git 仓库；文件系统快照；仅工具级撤销日志 |
| D2 覆盖范围 | 覆盖采集范围内的全部变更，包含被允许的工作区脚本造成的变更 | 只覆盖内置工具的写入；默认只覆盖工具写入、可选扩展 |
| D3 敏感文件 | 不采集内容也不采集内容摘要，只记录存在性与元数据；回滚只报告不改写 | 采集内容并限制权限或加密；采集内容摘要 |
| D4 保留与清理 | 按运行数保留加总量上限，在新运行采集之前清理，另有显式的列出与删除入口 | 永久保留；成功运行后立即删除；按时间过期 |

这些规则改变开发规范 §10（新增 §10.5）和 §13（新增 §13.4），并细化 §16 阶段 F 的实现清单与退出条件。第 2 节红线不变。

### D1 存储方式

我们将在运行开始、第一次模型调用之前，把工作区的基线内容采集为一份运行级检查点：

- 位置 `<workspace>/.proofcoder/checkpoints/<run_id>/`，与现有的 `runs/<run_id>/` 并列，沿用 0o700 目录权限和同一套工作区内路径校验。
- 结构是 `manifest.json` 加 `blobs/<摘要前两位>/<摘要>`。清单的每个条目记录工作区相对 POSIX 路径、字节数、权限位、内容 `sha256` 和对应 blob；内容相同的文件只存一份 blob。
- 采集范围是工作区内的普通文件，排除 `list_files` 的默认忽略目录（`.git`、`.venv`、`venv`、`node_modules`、`__pycache__`、`.pytest_cache`、`.ruff_cache`、`.mypy_cache`、`.proofcoder`、`.proofcoder-runs`）、符号链接和非普通文件。
- 单文件内容上限与文件工具一致（1 MiB）。超过上限的文件只记录路径与元数据，标记为“可检测、不可恢复”，不复制内容。
- 检查点有条目数和总字节上限。采集超限或失败时，运行默认不启动并返回结构化错误；用户可以用显式开关放弃检查点保护后再运行。

采集在写入发生之前一次完成，因此覆盖范围不依赖“谁执行了写入”，这是能同时覆盖工作区脚本的前提。

### D2 覆盖范围

我们将让回滚覆盖采集范围内的全部变更，而不只是内置工具的写入：

- 相对基线内容发生变化的文件，原子写回基线内容。
- 运行期间新出现、基线中不存在的路径，删除。
- 运行期间被删除的文件，按基线重建，包括权限位。
- 结果对每个路径标注来源：轨迹中有对应成功修改事件的标为工具写入，其余标为其它来源（工作区脚本、构建产物或用户的并发编辑）。
- 回滚只能由用户显式触发，不在运行结束时自动执行。执行前先给出将要恢复、删除和重建的完整清单，由用户确认。
- 明确不在覆盖范围内的部分必须在结构化结果中单独列出，不得静默跳过：工作区之外的路径、`.git` 内部状态、被忽略目录、超过单文件上限的文件、敏感路径（见 D3）、以及回滚过程中写入失败的文件。

### D3 敏感文件

我们将把敏感路径整体排除在检查点内容之外：

- 采集时，`is_sensitive_path` 命中的路径只记录相对路径、字节数、mtime 和权限位，既不复制内容，也不记录内容摘要。摘要是由凭据派生的产物，对低熵文件可以用猜测确认，因此不写入运行产物。
- 回滚时不写入、不删除、不重建任何敏感路径。运行期间这些路径发生变化、新出现或消失，都作为结构化结果中的独立分组报告给用户。
- 这样满足开发规范 §2.3 和 §16 阶段 F 的“检查点不得把凭据内容写入运行产物”，也与文件工具本来就拒绝读写这些路径的行为一致。
- 代价是：工作区脚本破坏 `.env` 或私钥时，ProofCoder 无法恢复，只能报告。README 和威胁模型必须写明这条覆盖缺口。

### D4 保留与清理

我们将用可离线验证的确定性规则控制检查点占用：

- 默认保留最近 3 次运行的检查点，数量可配置，并设总字节上限。
- 清理发生在新运行采集基线之前，按运行开始时间从旧到新删除，绝不删除正在进行的运行的检查点。不使用后台线程或定时任务。
- 清理检查点不删除运行轨迹。`runs/<run_id>/` 是审计记录，保留规则不受本决策影响；轨迹中记录“检查点已过期”这一事实。
- 回滚成功后保留该检查点直到按上述规则过期，使重复回滚幂等。
- 另外提供显式的列出与删除入口（阶段 F.3 的命令行子命令），让用户可以立即释放空间。

## 备选方案

### D1 存储方式

- **维持现状（不建立检查点）。** 成本为零，但模型的误改无法撤销，并且按 ADR-0003 会一直阻塞阶段 G 和 H。未选。
- **影子 Git 仓库。** 用 `--git-dir=.proofcoder/checkpoint.git --work-tree=<workspace>` 在运行前提交一次，回滚用 `git read-tree` 或 `checkout`。优点是增量存储、压缩和成熟的差异能力。未选：它把外部 `git` 可执行文件变成回滚能力的硬依赖（§2.4 要求优先用标准库，且外部可执行文件是供应链与信任边界）；`git` 默认按 `.gitignore` 跳过文件，而被忽略但真实存在的文件（构建产物、本地配置）恰恰是脚本最常改动的对象，会形成用户看不见的覆盖缺口；还要处理用户仓库的索引锁、hooks、`safe.directory`、行尾转换和 Windows 权限差异；默认还会把 `.env` 内容写进 Git 对象库，与 D3 直接冲突。
- **文件系统快照（btrfs、ZFS、APFS、Windows VSS）。** 采集接近零成本且最完整。未选：依赖特定文件系统和管理员权限，在跨平台 CI 和离线测试里不可用，不能作为基线能力。
- **仅工具级撤销日志。** 在 `create_file` 和 `replace_in_file` 写入前记录 before-image，复用已有的 `FileSnapshot`。优点是几乎零成本、零冗余，且与采集范围无关。未选：它按定义只能覆盖本项目自己的写入，无法覆盖 `python <脚本>.py`、`g++ -o` 和测试副作用，不满足阶段 F 的退出条件。其覆盖的文件本来就被 1 MiB 上限约束，因此影子副本方案已经完整包含它的能力。

### D2 覆盖范围

- **维持现状（无回滚）。** 见 D1。未选。
- **只覆盖内置工具的写入。** 采集量最小，且只动“确实是 agent 改的”文件，不会误删构建产物或用户的并发编辑。未选：它把脚本造成的破坏留在原地，而放宽命令策略正是阶段 H 的目标，ADR-0003 要求先具备控制手段；开发规范 §16 阶段 F 也明确要求覆盖被允许的工作区进程。
- **默认只覆盖工具写入，用显式开关扩展到全部变更。** 默认安全、需要时完整。未选：默认值决定了绝大多数实际结果，“默认不收拾脚本造成的破坏”等于把主要风险留给用户自己发现；D2 推荐方案用“显式触发加确认清单”达到同样的谨慎程度，而不牺牲默认覆盖面。
- **把工作区之外的写入也纳入回滚。** 破坏面确实存在于工作区之外。未选：程序无法可靠地知道脚本在宿主上写了什么，采集整个用户目录既不可行也不可接受；该风险由阶段 L 的操作系统级隔离处理，在此之前作为剩余风险记录在威胁模型中。

### D3 敏感文件

- **维持现状（文件工具拒绝，检查点不特别处理）。** 在没有检查点时是自洽的。未选：一旦开始采集内容，默认行为就会把 `.env` 复制进 `.proofcoder/`，与 §2.3 和阶段 F 退出条件冲突。
- **采集内容，但限制权限或加密存储。** 能完整恢复被脚本破坏的凭据文件。未选：0o700 只防其他本地用户，挡不住备份、同步、打包和误传；加密需要另一个密钥，而项目只允许凭据来自环境变量，等于引入新的凭据管理问题；开发规范 §16 明确禁止把凭据内容写入运行产物。
- **只采集内容摘要，不采集内容。** 能精确判断敏感文件是否被改动，且不直接存储内容。未选：摘要仍是由凭据派生的产物，对结构固定、长度较短的文件可以用猜测确认；用元数据（大小、mtime）做变化提示已经足以发出警告，不值得为提高判定精度而留下派生产物。若以后需要更精确的检测，可以用运行级随机盐的 HMAC 另写一篇 ADR。
- **完全忽略敏感路径，连元数据也不记录。** 最保守。未选：这样用户无法知道运行期间 `.env` 被改写或删除，而这恰恰是最需要提醒的事件。

### D4 保留与清理

- **维持现状（永久保留，只增不减）。** 实现最简单，并且永远可以回滚任意历史运行。未选：检查点位于用户仓库内部，体积远大于轨迹，无上限增长不可接受；开发规范 §16 阶段 F 明确要求存储上限。
- **运行成功完成后立即删除检查点。** 占用最小。未选：最常见的回滚场景恰恰是“运行成功完成，但改动不是用户想要的”，删除后这个场景无法覆盖。
- **按时间过期（例如保留 7 天）。** 与用户的直觉一致。未选：依赖系统时钟，离线测试需要冻结时间或注入时钟，确定性不如按运行数；并且时间策略仍然需要一个总量上限来兜底。可以在阶段 M 作为可选配置补充。
- **把检查点放到工作区之外（例如用户缓存目录）。** 不污染用户仓库。未选：跨平台的缓存目录语义不一致，且会让运行产物脱离“工作区内、被 Git 忽略、可随工作区一起删除”的现有模型；工作区内的 `.proofcoder/` 已经被忽略规则覆盖。

## 后果

- **正面：**
  - 任意一次运行结束后，采集范围内的文件都可以恢复到运行前的内容，包括中断、预算耗尽和内部错误终止。
  - 覆盖范围包含被允许的工作区脚本，这是 ADR-0003 为阶段 G 和阶段 H 设定的前提条件。
  - 检查点不含凭据内容，运行产物的敏感面不比现在的轨迹更大。
  - 存储与清理规则是确定性的，可以在离线测试中完整验证。
- **负面与新增风险：**
  - 每次运行开始都要读取并复制采集范围内的文件，大工作区上有可感知的启动开销和磁盘占用。上限与清理规则限制了上界，但不能消除开销。
  - 全覆盖回滚会撤销运行期间发生的其它变更，包括用户的并发编辑和脚本刻意生成的产物。缓解手段是显式触发、确认清单和来源分类，不是自动判断意图。
  - 敏感路径、超限文件、被忽略目录、`.git` 内部状态和工作区之外的写入都不可恢复，这些缺口必须在文档中写明，不能让“可回滚”被理解为完全可逆。
  - 采集与恢复都存在检查时刻与使用时刻的竞态；恢复写入沿用现有的原子替换与快照复核，但不能消除竞态。
  - `.proofcoder/checkpoints/` 会保存工作区文件的副本。工作区内的普通文件若本身含有敏感信息但不匹配敏感路径规则，其副本同样会进入检查点。
- **需要同步修改：** 开发规范 §10.5（新增）、§13.1 与 §13.4（新增）、§15.1、§16 阶段 F、§17；`docs/ROADMAP.md`；`CHANGELOG.md`。实现合并时还需要更新 `README.md`、`docs/DESIGN.md`、`docs/THREAT_MODEL.md` 和 `docs/COMPLIANCE.md`。

## 验证

- 开发规范 §16 阶段 F 的退出条件，以及 v3.0 阶段通用退出条件。
- 阶段 F.2 的离线单元测试至少覆盖：采集范围与忽略目录；超限文件只记录元数据；敏感路径不产生 blob；工具写入、脚本写入、新增文件和删除文件四类变更都能恢复；部分恢复失败时报告未恢复的路径；重复回滚幂等；保留数量与总量上限的清理顺序；不清理进行中的运行；跨平台的权限位与换行处理。
