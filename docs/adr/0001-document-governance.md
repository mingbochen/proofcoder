# ADR-0001：分层文档治理与架构决策记录

- 状态：已接受
- 日期：2026-09-13
- 决策者：chenmingboi（仓库作者）
- 相关：开发规范 §17、§18；`AGENTS.md`；`CLAUDE.md`；ROADMAP 阶段 0

## 背景

- 阶段 A–E 由一份开发规范驱动，规范同时承担约束和阶段计划两种职责。
- 约束调整没有固定的记录位置。例如实现浏览器界面时，偏离“图形界面是非目标”的理由只写在 README 的一段话里。
- 项目进入长期演进，一个目标通常需要多次对话和多个 PR 才能完成，每次开始时都要重新确定进度。
- 开发智能体的对话记忆保存在开发者本机，不在仓库中，不能承载长期约束。
- 2026-09-13 的开发对话中观察到：Claude Code 没有自动读取 `AGENTS.md`，仓库规则只能靠智能体主动读取。
- 开发规范 §1 把“可解释性：关键设计具有明确的备选方案、取舍和测试依据”列为工程属性，但没有记录备选方案的固定位置。

## 决策

我们采用按改动频率分层的文档体系，各文档职责写入开发规范 §18：

- `docs/DEVELOPMENT_SPEC.md`：规范性约束，只在阶段开始时经用户批准修改。
- `docs/adr/`：约束为什么这样定、为什么改变；已接受的 ADR 不修改正文。
- `docs/ROADMAP.md`：阶段与小项的进度，每个合并的变更都更新。
- `CHANGELOG.md`：用户可感知的变化。
- `AGENTS.md`：开发流程。`CLAUDE.md` 通过 `@AGENTS.md` 导入它，使 Claude Code 每次对话自动加载。
- `.github/pull_request_template.md`：每个 PR 的阶段归属、约束变化和文档同步清单。
- 能由程序判断的文档一致性纳入合规检查（ROADMAP 小项 0.3）。

## 备选方案

- **维持现状，只用开发规范。** 不增加文档，但规范会混入进度而频繁修改，约束变化的理由仍然缺失。未选。
- **把路线图写进开发规范。** 只有一份文档，但规范会变成易变文档，削弱“必须成立”的权威。未选。
- **用 GitHub Issues 或 Projects 管理路线。** 协作方便，但不随代码版本化，离线时和开发智能体都不便读取。可以作为补充，不作为唯一来源。未选。
- **写一篇大的愿景文档。** 集中表达方向，但会与规范内容重叠并逐渐矛盾。未选。

## 后果

- **正面：** 约束变化可以追溯；任何一次对话都能从 ROADMAP 恢复进度；Claude Code 自动加载仓库规则。
- **负面与新增风险：** 每个 PR 多了文档维护成本。多份文档之间仍可能漂移，在小项 0.3 的机械检查完成之前，只能靠 PR 清单约束。
- **需要同步修改：** 开发规范 §17、§18；`AGENTS.md`；新增 `CLAUDE.md`、`CHANGELOG.md`、`docs/ROADMAP.md`、`docs/adr/` 和 PR 模板；README 的文档表。

## 验证

- 每个 PR 都填写 PR 模板的清单。
- ROADMAP 小项 0.3 完成后，文档一致性由 CI 检查。
