# ADR-0003：v3.0 范围与非目标调整

- 状态：已接受
- 日期：2026-09-13
- 决策者：chenmingboi（仓库作者）
- 相关：开发规范 §1.2、§3、§16、§17；ROADMAP 阶段 F–M；ADR-0001；ADR-0002

## 背景

开发规范 v2.1 为了让阶段 A–E 保持可控，设置了较窄的范围。阶段 A–E 已经完成，项目目标转为可以在真实仓库中长期使用。以下限制在 v2.1 下是合理的取舍，现在成为主要瓶颈（均为 2026-09-13 的实现事实）：

- 文件工具只有新建和精确替换。`create_file` 要求父目录已经存在，并且不覆盖任何已有路径；没有删除、移动或创建目录的工具。
- 命令策略允许的可执行对象基本限于 Python 生态（`python`/`py`、`pytest`、`ruff`、`unittest`、`compileall`），外加只读 `git` 和受限的 `g++`；不能安装依赖，也不支持其他语言的构建工具。
- 模型接口只有 DeepSeek，而且是非流式响应。
- 每次运行都新建消息历史，同一工作区的多次任务之间不共享上下文。
- 上下文预算按字节而不是 token 计算，也没有仓库级的结构理解。
- 命令执行没有操作系统级隔离，被允许的工作区脚本拥有当前用户的全部权限。
- 真实模型评测只有 3 个小型 Python fixture。

## 决策

我们按下表调整约束，并按开发规范 §16 的阶段逐步实现。每一项在对应阶段开始时，还要写一篇细化设计的阶段 ADR。

| 约束 | 决策 | 阶段 | 前提 |
| --- | --- | --- | --- |
| 新建不覆盖、父目录必须存在；没有删除、移动、创建目录 | 放宽，新增对应工具 | G | 阶段 F 的回滚 |
| 命令窄白名单；需要确认的命令一律阻断 | 保留默认拒绝，增加项目级策略和人工审批 | H | 阶段 F 的回滚 |
| 不自动提交 Git | 改为运行前检查点；自动提交、推送、创建 PR 仍是非目标 | F | — |
| 多模型路由和通用厂商插件是非目标 | 可替换的提供方纳入范围；按能力或成本自动路由仍是非目标 | J | — |
| 非流式响应 | 支持流式，保留非流式作为回退 | J | 流式 tool call 在本地拼接和校验 |
| 长期记忆是非目标 | 工作区内的多轮会话纳入范围；向量数据库和跨工作区记忆仍是非目标 | I | — |
| 按字节计算上下文预算 | 改为按 token 计算，并加入仓库结构摘要 | K | 阶段 I 的会话模型 |
| 完整操作系统沙箱是非目标 | 纳入范围 | L | 阶段 G、H |
| MCP 是非目标 | 暂缓，阶段 H 完成后重新评估 | — | 人工审批机制 |
| 图形界面是非目标 | 已由 ADR-0002 移出；复杂 TUI 仍是非目标 | — | — |

以下约束明确保持不变：

- 开发规范第 2 节的全部红线：不使用 agent 框架或 SDK；不依赖服务端托管的执行或文件能力；agent 核心逻辑由本仓库实现；凭据只来自环境变量。
- 证据门控的完成判定：完成状态只由本地执行证据决定；多轮会话中，验证结果也不跨运行继承。
- 同步主循环：阶段 H 等待审批的问题也在同步模型内解决；如果要引入并发，必须另写 ADR。
- 多 agent、子 agent 和模型投票仍是非目标。
- 放宽写入和命令能力之前，必须先具备回滚能力：阶段 F 先于 G 和 H 完成。

## 备选方案

- **保持 v2.1 范围。** 实现和审查成本最低，但工具与命令的限制使项目无法用于真实仓库。未选。
- **一次性放开工具与命令。** 进度最快，但没有回滚和审批时，模型造成的误删、误覆盖和不当命令都无法撤销。未选。
- **引入 agent 框架加速开发。** 违反第 2 节红线，也会失去项目自有 agent loop 这一核心价值。未选。
- **先做操作系统隔离（阶段 L），再放宽工具。** 隔离对多数风险的控制最彻底，但工作量大、跨平台差异大，会长期阻塞其他能力；回滚加审批能以更低成本先控制主要风险。未选，隔离安排在 G、H 之后。

## 后果

- **正面：** 项目有了用于真实仓库的路径；每条约束的放宽都明确了前提和所属阶段。
- **负面与新增风险：** 删除、覆盖和更宽的命令范围扩大了潜在破坏，在阶段 L 之前只能靠回滚与审批控制；多提供方和流式响应增加了协议测试的负担；阶段数量多，文档维护成本上升。
- **需要同步修改：** 开发规范 §1.2、§3、§16、§17；README；ROADMAP。
