# ADR-0008：可替换模型提供方与流式响应

- 状态：已接受
- 日期：2026-09-15
- 决策者：chenmingboi（仓库作者，五项决策均委托本次提案的推荐方案）
- 相关：开发规范 §2.1、§2.2、§2.4、§4.2、§4.6、§5.1、§8.2、§11.2、§13.1、§15.2、§16 阶段 J、§17；ROADMAP 小项 J.1；ADR-0002（浏览器界面）、ADR-0003（阶段 J 的范围）

## 背景

阶段 I 已合并。阶段 J 是 v3.0 里唯一改变「模型怎么被调用」的阶段。以下是 2026-09-15 的实现事实：

- 提供方的接缝已经存在但只有一条实现。`llm/base.py` 里的 `LLMClient` 只有一个方法 `complete(messages, tools) -> ModelResponse`，`llm/deepseek.py` 是唯一的生产实现，`llm/scripted.py` 是离线测试用的实现。
- `DeepSeekClient` 已经在做「只负责通信和协议对象转换」这件事：它把 openai SDK 的响应对象转成本仓库自己的 `ModelResponse`、`ToolCall`、`FunctionCall`、`TokenUsage`，把 SDK 异常分类成 `LLMErrorCategory`，并显式关掉 SDK 自身的重试。
- 但配置还是单提供方形状的：`ProofCoderConfig` 只认 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`、`DEEPSEEK_REASONING_EFFORT` 四个环境变量，没有「选哪个提供方」这一维。
- 重试策略已经是提供方无关的：`retry.py` 只看 `LLMErrorCategory` 和状态码，不认识任何厂商。
- `AgentLoop` 是同步的，一次 `_request_model` 拿到一个完整的 `ModelResponse` 之后才继续。上下文预算的字节计量、协议修复、工具批次校验全都建立在「拿到完整响应」之上。
- 浏览器界面是长轮询已提交事件的：`_BrowserRunSink` 把事件追加进内存缓冲，页面轮询 `wait_for_events`。页面今天没有任何「一个事件正在生成中」的表示。
- 金标轨迹（`tests/golden/trace_golden.jsonl`）逐字节固定了非流式路径产生的事件序列。
- 第 2.4 节依赖边界规定运行时依赖要有明确理由；第 2.2 节要求输出解析由本仓库实现；第 2.1 节禁止依赖 API 托管的执行能力。

## 决策

我们将按下表实现阶段 J。五个决策点都在“备选方案”中给出取舍，下表是推荐方案，五项均已获批准。

| 决策点 | 决策 | 落选的主要方案 |
| --- | --- | --- |
| D1 第二个提供方选谁 | 本地模型 Ollama，用标准库 HTTP 直接对接它的原生 `/api/chat`，不新增运行时依赖 | 接入 Anthropic SDK；只换一个 OpenAI 兼容端点；接入多个厂商 |
| D2 接缝划在哪 | `LLMClient` 保持只有 `complete` 一个必需方法；提供方适配层只做通信与协议对象转换，错误一律翻译成既有的 `LLMErrorCategory` | 让 AgentLoop 知道提供方；把重试下放给各 SDK |
| D3 流式响应给循环看什么 | 适配层把流拼装并校验成与非流式**同一个** `ModelResponse` 再交给循环；流只影响呈现，不影响判定 | 让 AgentLoop 消费流；流式与非流式走两条判定路径 |
| D4 流式 tool call 的拼装 | 按 index 拼装，id 与函数名一次确定后不得改变，参数 JSON 在交给循环之前整体校验；中断、截断、非法 JSON 各自转成结构化错误，绝不部分执行 | 边收边解析部分参数；把不完整的 tool call 交给循环去修 |
| D5 默认走哪条路 | 非流式仍是默认，流式按运行显式开启；流中途失败是结构化错误，交既有重试策略处理，不静默重发 | 默认流式；流失败时自动改用非流式重发一次 |

这些规则新增开发规范 §4.7（提供方与流式）和 §11.5（流式失败的分类），修改 §4.2、§4.6、§5.1 和 §13.1，并细化 §16 阶段 J 的实现清单与退出条件。第 2 节红线不变。

### D1 第二个提供方选谁

第二个提供方是**本地模型**：通过 Ollama 的原生 `/api/chat` 接口，用标准库 `urllib` 直接发请求。

规范 §16 阶段 J 要求「在 OpenAI 兼容接口之外，至少再接入一种提供方或本地模型」。选本地模型而不是再接一家云厂商，有三个理由：

1. **它真的是另一套协议。** 再接一个 OpenAI 兼容端点只是换个 base URL，证明不了接缝成立——现在的代码换个 `DEEPSEEK_BASE_URL` 就能做到。Ollama 的原生接口有自己的消息形状、自己的 tool call 表示、自己的流式分帧，适配层必须真的做转换，接缝是否只承担「通信与协议对象转换」才会被检验。
2. **它不新增运行时依赖。** 用标准库 HTTP 对接，`pyproject.toml` 的运行时依赖不变。接 Anthropic 会引入第二个 SDK，而第 2.4 节要求依赖有明确理由——「为了证明抽象成立」不是一个好理由。
3. **它不需要第二个付费凭据。** 评测和日常开发不会因为想验证接缝而多一份账单和多一处密钥管理面。

配置增加一维提供方选择：`PROOFCODER_PROVIDER`，取值 `deepseek`（默认）或 `ollama`。现有四个 `DEEPSEEK_*` 变量保持原样，Ollama 用自己的 `OLLAMA_*` 变量，因为把两家的配置挤进同一组变量名会让「哪个变量对哪个提供方生效」变成要读代码才知道的事。不设置 `PROOFCODER_PROVIDER` 时，行为与阶段 J 之前逐字节一致。

本地提供方不要求任何凭据，所以 `doctor` 对它的检查是「端点是否可达」，不是「密钥是否设置」。

### D2 接缝划在哪

`LLMClient` 继续只有 `complete` 一个必需方法。流式是可选能力（见 D3），不是协议的第二个必需方法：一个不支持流式的提供方必须仍然是合法的 `LLMClient`。

适配层的职责边界写死为两件事：**通信**，以及**协议对象转换**。具体说：

- 进来的是本仓库自己的消息与工具 schema，出去的是本仓库自己的 `ModelResponse`。提供方特有的对象不得越过适配层。
- 提供方的异常翻译成既有的 `LLMErrorCategory`。`retry.py` 已经只认这些类别，所以重试策略天然是提供方无关的，且必须保持如此——适配层不得自己重试，也不得开启 SDK 自带的重试。
- 适配层不得决定终止、不得判定完成、不得改写历史。这些都在第 2.2 节的「必须自行实现」清单里。

退出条件「AgentLoop 的行为与提供方无关」用一条测试固定：同一段脚本化的响应序列，经过两个不同的适配层进入循环，产生的事件序列与终止结果相同。

### D3 流式响应给循环看什么

流由适配层消费并拼装成与非流式**完全相同**的 `ModelResponse`，然后才交给 `AgentLoop`。循环不知道这次响应是不是流式来的。

这样划的理由是：一旦循环消费流，上下文字节计量、协议修复、工具批次完整性校验就都要处理「还没收完」这个中间状态，而这些正是第 2.2 节要求本仓库自己实现、也是本项目最不该出错的地方。让流只影响呈现，判定路径就只有一条。

流式带来的可见变化只有一个：适配层接受一个可选的增量回调，把已经收到的可见文本片段交给调用方。命令行用它打印增量文本，浏览器用它做增量渲染。这个回调只接收模型的**可见文本**，不接收 tool call 片段——半个 tool call 不是给人看的东西，把它显示出来只会让人以为某个操作已经开始了。

金标轨迹不需要重新生成：流式不新增事件类型，也不改变事件内容。如果某次改动让它变了，那说明流式漏进了判定路径。

### D4 流式 tool call 的拼装

拼装规则写死，且全部在交给循环之前完成：

- 片段按 provider 给的 index 归并。第一次出现时确定 id 与函数名，之后再出现不同的 id 或函数名是协议错误，不是覆盖。
- 参数是字符串拼接，拼完之后整体做一次 JSON 解析。不做增量解析，也不对半截参数做任何猜测。
- 流在拼装完成前结束（连接断开、超时、被中断），记为结构化错误；参数拼完但不是合法 JSON，记为结构化错误；片段数量或总长度超过上限，记为结构化错误。
- 任何一种失败都不产生部分执行：要么整批 tool call 合法并交给循环，要么这次响应就是一次失败的模型调用。

这些错误沿用既有分类：可重试的（连接、超时）走 `retry.py` 已有的路径，不可重试的（非法 JSON、协议冲突）按永久错误处理。新增 §11.5 只是把「流式拼装的失败如何归类」写明，不新增错误层级。

### D5 默认走哪条路

非流式是默认。流式按运行显式开启（`proofcoder run --stream`，浏览器界面一个开关）。

理由有两条，都关于可复现性：

- 评测必须是确定性的。评测一律走非流式路径，不提供开关——流式引入的是网络分帧的时序，不是模型行为的差异，让它进入评测只会增加噪声。
- 非流式路径必须保持可用，这是退出条件明写的。把它降级为「流式不可用时的兜底」会让它逐渐失修。

流中途失败**不**自动改用非流式重发。那样做会把一次失败变成两次请求、两份计费和一条看不出发生过什么的轨迹。失败就是失败，交给既有重试策略，重试仍然走流式。

## 备选方案

**维持现状（不做阶段 J）。** 只有一个提供方、只有非流式。优点是没有任何新代码。缺点是 `LLMClient` 这条接缝从未被第二个实现检验过——一个只有一个实现的抽象，不能声称自己是抽象；而且长任务里用户在第一个 token 到最后一个 token 之间看不到任何东西。ADR-0003 已经把阶段 J 列入 v3.0 范围。

**接入 Anthropic SDK 作为第二个提供方（D1 的落选项）。** 优点是它是一套真正不同的协议，且原生 tool calling 成熟。没有选是因为它引入第二个运行时 SDK 依赖和第二份付费凭据，而本阶段的目的是检验接缝，不是增加厂商覆盖。如果将来有人真的要用 Anthropic，本阶段做出的接缝正是让那件事变成小改动的东西。

**只换一个 OpenAI 兼容端点（D1 的落选项）。** 优点是几乎零成本。没有选是因为它证明不了任何事：今天改一个环境变量就能做到，适配层一行都不用动。

**让 AgentLoop 消费流（D3 的落选项）。** 优点是理论上首字延迟最低，且循环能在工具调用出现的瞬间就开始准备。没有选是因为它把「响应还没收完」这个状态引入上下文管理、协议修复和批次校验三处，而这三处是第 2.2 节点名要求本仓库自己实现、出错代价最高的地方。收益是延迟，代价是判定路径翻倍。

**边收边解析 tool call 参数（D4 的落选项）。** 优点是能更早地把参数展示出来。没有选是因为半个 JSON 的任何解释都是猜测，而猜测过的参数一旦进入执行路径，就没有办法再区分「模型要求的」和「我们补全的」。

**默认流式（D5 的落选项）。** 优点是默认体验更好。没有选是因为默认路径应该是那条被评测、被金标轨迹、被绝大多数测试覆盖的路径。

**流失败时自动改用非流式重发（D5 的落选项）。** 优点是用户更少看到失败。没有选是因为它把一次失败变成两次请求和两份计费，而轨迹里看不出发生过什么。

## 后果

- **正面：**
  - `LLMClient` 这条接缝第一次有两个形状完全不同的实现，抽象是否成立变成可检验的事实而不是声明。
  - 增加一条不需要凭据、不需要网络的本地模型路径，评测与开发都不再必须有云端 key 才能跑真实模型。
  - 长任务里可见文本可以增量呈现，而判定路径没有增加。
  - 流式拼装的每一种失败都有确定的分类和确定的后果，不存在「部分执行」。
- **负面与新增风险：**
  - 多了一条协议转换路径，就多了一处协议漂移的可能。用「同一脚本序列经两条适配层产生相同事件」的测试守住。
  - 本地模型的工具调用质量通常低于云端模型，评测数据不能跨提供方比较。这一点要在评测报告里写明，而不是让两组数字并排出现。
  - `doctor` 的检查要按提供方分叉，命令行输出因此多一种形状。
  - 流式代码的离线测试需要能重放分帧，`ScriptedClient` 要能扮演一个流。
- **需要同步修改：** 开发规范 §4.2、§4.6、§4.7（新增）、§5.1、§11.5（新增）、§13.1、§15.2、§16 阶段 J；`docs/ROADMAP.md` 的阶段 J 小项拆分；`CHANGELOG.md`。实现落地时还需要修改 `README.md`、`docs/DESIGN.md`、`docs/THREAT_MODEL.md` 和 `docs/COMPLIANCE.md`——按 §18.2，这些事实性文档只描述已合并的行为。§5.1 的目录树在新模块实际存在时才改，因为合规检查 `documentation.spec_layout` 要求树中每个路径都存在。

## 验证

- 提供方无关性：同一段脚本化响应序列经两个适配层进入循环，事件序列与终止结果逐项相同。
- 适配层边界：适配层不得出现终止判定、完成判定或历史改写；提供方特有的对象不出现在 `AgentLoop` 的任何入参与出参里。
- 流式与非流式等价：同一段响应，流式拼装出的 `ModelResponse` 与非流式返回的逐字段相等。
- 流式失败分类：连接中断、超时、片段超限、参数非法 JSON、id 或函数名中途改变，各自返回确定的结构化错误，且都不产生任何工具执行。
- 重试仍然提供方无关：`retry.py` 不引入任何提供方名称，流式失败按既有类别重试。
- 默认行为不变：不开启流式、不设置提供方变量时，金标轨迹不需要重新生成。
- 本地提供方的 `doctor` 检查不要求凭据，且在端点不可达时给出可行动的原因。
